
# История версий xraypanel

Ниже — журнал изменений: что добавлялось и что исправлялось в каждой версии.
Свежие записи идут выше старых. Действующее описание проекта — в файле
[README.md](README.md).

## Стрелки без перезагрузки (напоминание о подтверждении) (0.58.0)

После перестановки правил стрелками на странице сразу появляется подсказка
«Порядок правил изменён — нажмите «Подтвердить конфиг»», чтобы не забыть применить
изменение.
# xraypanel — веб-панель xray для OpenWrt / ImmortalWrt 23.05

Ставится как обычный пакет (`opkg install xraypanel_0.19.0_all.ipk`), панель
доступна в браузере: `http://<IP роутера>/cgi-bin/xraypanel`.

## Что умеет

- серверы (выходы VLESS + Reality): добавить, изменить, удалить;
- добавление сервера вставкой ссылки `vless://` (Reality) — поля заполняются сами;
- реверс-мосты (обратные туннели к серверу-порталу): тег + домен + через какой выход;
- правила маршрутизации: по IP или домену → в нужный выход;
- проверка задержки серверов (ping) и выбор «основного» сервера;
- кнопка «Выбрать лучший по пингу»: панель сама замеряет все серверы и ставит самый быстрый;
- режим «автовыбор по пингу»: xray держит балансировщик leastPing и сам уходит на самый быстрый сервер;
- прозрачный режим: трафик выбранных клиентов, всей сети или самого роутера заворачивается в xray;
- применение конфига: генерация → проверка `xray run -test` → бэкап → перезапуск;
- откат на предыдущий конфиг (хранятся последние 10 копий);
- просмотр конфига и журнала xray;
- необязательный пароль на вход в панель.

## Файлы

- `/www/cgi-bin/xraypanel` — сама панель (CGI, работает через uhttpd);
- `/usr/lib/xraypanel/lib.sh` — генерация конфига, применение, откат;
- `/etc/config/xraypanel` — настройки и модель (серверы, мосты, правила) в UCI;
- `/etc/xray/config.json` — итоговый конфиг xray (генерируется панелью);
- `/etc/xraypanel/config.*.bak` — резервные копии конфига.

## Установка

    scp xraypanel_0.19.0_all.ipk root@<IP роутера>:/tmp/
    ssh root@<IP роутера> 'opkg install /tmp/xraypanel_0.19.0_all.ipk'

Пакет — это gzip-архив (формат ipk в OpenWrt 23.05+), поэтому при желании
его содержимое можно посмотреть так:

    cd /tmp && tar tzf xraypanel_0.19.0_all.ipk

Если `opkg` ругается на зависимости, помогает:

    opkg install --nodeps /tmp/xraypanel_0.19.0_all.ipk

## После перезагрузки роутера всё применяется заново (0.31.0)

Была проблема: после перезагрузки настройки в панели на месте, а часть правил
«не работает» — в основном это касалось маршрутов через интерфейс (правила
вида «через интерфейс wan») и правил прозрачного режима. Причины две:

- маршруты через интерфейс живут в ядре и привязываются к шлюзу; после
  перезагрузки провайдер подключается позже, шлюз другой, и правила остаются
  со старым адресом — то есть не работают;
- правила прозрачного режима могли ставиться раньше, чем поднималась служба
  xray (а если xray не поднялся, то трафик вообще заворачивался в порт, который
  никто не слушает).

Что теперь:

- добавлен скрипт автозапуска по событию сети (`/etc/hotplug.d/iface/99-xraypanel`):
  когда интерфейс поднимается или провайдер переподключается, панель заново
  применяет маршруты через интерфейс и правила прозрачного режима — уже с
  новым шлюзом;
- служба автозапуска панели теперь ждёт xray (в фоне, не задерживая загрузку) и
  ставит правила только если служба действительно работает; иначе правила не
  ставятся, и интернет у клиентов не пропадает;
- что именно произошло при загрузке, видно в журнале прозрачного режима на
  странице «Прокси» — там появляются строки вида «загрузка: правила
  прозрачного режима восстановлены».

## Пинг без перезагрузки, клиенты сверху, плашки доменов (0.56.0)

**«Замерить пинг» больше не перезагружает страницу.** Кнопка теперь работает
как «проверить»: она по очереди опрашивает серверы в фоне, и значения
появляются прямо в столбце «Пинг» (во время замера в ячейке видно «…»).

**Выбор клиентов переехал наверх** — сразу под кнопки «Управление», как самое
нужное при настройке перехвата. Раскладка сделана гибкой (`order` в форме), так
что порядок такой: состояние → кнопки → клиенты → настройки.

**Короткие подписи источников трафика:** «(роутер)» — счётчики фаервола самого
роутера, «(xray)» — статистика xray. Счётчики роутера не сбрасываются при
перезапуске xray, но обнуляются, когда правила перехвата ставятся заново;
счётчики xray живут до перезапуска xray.

**В отчёте «подобрать правило для домена» каждое название — плашка:** при
наведении подсвечивается, при клике копируется в буфер (и на секунду пишет
«скопировано»). Цвета чередуются, чтобы список читался. Разбор правил и подсказки
остались прежними.

## Разгрузка страниц и компактные настройки (0.55.0)

**«Маршруты» стали быстрее.** Убраны столбец «Трафик» и тексты в колонке
«Работает» — осталась только лампочка (зелёная — трафик шёл только что, жёлтая
— в последние минуты, серая — давно; подробности в подсказке при наведении).
Главное: страница больше не запрашивает статистику у xray **для каждого правила
отдельно** — именно это и тормозило её сильнее всего.

**«Подобрать правило для домена» больше не отдаёт «Bad Gateway».** Разбор файлов
со списками (они большие) ограничен по времени: если не успел, панель честно
пишет об этом, но разбор правил всё равно показывает.

**«Статус» разгружен:** убраны список серверов (он есть на странице «Серверы»),
проверка статистики трафика, журнал применения конфига и журнал xray.

**«Серверы»:** вместо столбца «Трафик» — столбец «Пинг», который заполняется по
кнопке **«замерить пинг»** (она переехала сюда со «Статуса» и стоит рядом с
«проверить все»). Вызовов к статистике xray на этой странице больше нет.

**«Прокси» — компактные настройки.** Все окна идут одним столбиком одного
размера: подпись слева, поле по центру, пояснение справа в одну строку (что не
влезло — во всплывающей подсказке при наведении). Порядок: порт перехвата, порт
DNS, резолверы, кого заворачивать, интерфейсы, куда направлять, перехват DNS,
куда заворачивать DNS, как разрешать имена серверов, выход для DNS, как
выпускать DNS, проверка имени. Длинные пояснения убраны в раскрывающийся блок
«подробнее про DNS и перехват». Дублирующие кнопки «Сохранить и включить» и
«Подтвердить» снизу убраны — они есть вверху, в блоке «Управление».

## Меньше файлов: одна копия прежнего конфига и возврат при сбое (0.54.0)

Как это работало раньше (и почему файлов было много):

- при каждом применении панель делала копию **прежнего** конфига в каталоге
  настроек — с датой в имени (`config.20260919-091831.bak`), и такие файлы
  копились по десять штук;
- если файл на роутере принадлежал другой программе, рядом с основным
  конфигом появлялась ещё одна копия `config.json.bak-<дата>`.

Что теперь:

- панель держит **ровно одну** копию прежнего конфига — `config.prev.json`
  (перезаписывается при каждом применении);
- собранный конфиг по-прежнему сохраняется в `config.last.json` — на случай,
  если запись основного не удалась;
- копии с датой, оставшиеся от прежних версий, подчищаются при первом же
  применении (в журнале появляется строка «убраны старые копии конфига»);
- копия «чужого» конфига больше не кладётся рядом с основным — она уходит в
  каталог настроек, и хранится только последняя.

Заодно применение стало безопаснее: если после записи нового конфига служба
**не поднялась**, панель сама возвращает прежний конфиг (`config.prev.json`),
перезапускает xray и пишет об этом в журнал. Так роутер не остаётся без прокси
из-за одного неудачного применения. Кнопка «Откат конфига» осталась — она
работает с той же единственной копией; если она не нужна совсем, скажите —
уберу.

## Временный конфиг больше не появляется в каталоге конфига (0.53.0)

Проверено на живом xray 24.12.31: при запуске с ключом `-confdir` служба читает
**все** файлы `.json` из каталога конфига и склеивает их. При совпадении тегов
побеждает файл из каталога — в тесте xray прямо написал:

    [/tmp/xt/dir/junk.json] updated inbound with tag: api

Именно поэтому оставшаяся старая копия (`config.new.json`) могла подсовывать
серверы и правила, которых в панели уже нет.

Что сделано: панель больше **не пишет временный конфиг в каталог конфига** — он
собирается в каталоге настроек панели (`/etc/xraypanel/config.tmp.<номер>.json`),
проверяется там и только потом переименовывается на место основного. Значит:

- в каталоге конфига не появляется лишних `.json`, которые мог бы подхватить
  `-confdir`;
- недописанный временный файл не может попасть в работу, даже если служба
  перезапустится в этот момент;
- собранный конфиг по-прежнему сохраняется в
  `/etc/xraypanel/config.last.json` — на случай, если запись основного не удалась.

## Трафик у правил — отдельным столбцом (0.52.0)

В списке правил маршрутизации трафик вынесен в **отдельный столбец
«Трафик»**: раньше он приписывался к названию выхода и мог обрезаться, так что
его не было видно. Теперь у каждого правила своя ячейка, а в подсказке при
наведении написано, что это объём всего выхода (xray не считает трафик по
отдельным правилам маршрутизации) и что счётчики обнуляются при перезапуске
xray.

Для правил «по пингу» и «через интерфейс» в столбце так и написано: «по пингу»
и «мимо прокси» — у них отдельного счётчика нет.

## Лишние .json в каталоге конфига (0.51.0)

Нашлась причина странного поведения: служба xray запускается с ключом
**`-confdir`**, то есть читает **все** файлы `.json` из каталога конфига и
склеивает их. Если там остался старый файл (например, `config.new.json`),
он продолжает подсовывать серверы и правила, которых в панели уже нет:
удалённый сервер «продолжает работать», а новый не виден.

Что теперь:

- на странице «Статус» появляется предупреждение с полным списком лишних
  `.json` в каталоге конфига;
- рядом кнопка **«Убрать лишние .json из каталога конфига»** — она переименует
  их в `.bak-дата` (файлы остаются рядом, откатить можно в любой момент), чтобы
  xray их больше не читал;
- после уборки нужно нажать «Применить конфиг» — панель про это напомнит.

Свои временные файлы панель в этот список не включает: она их и так убирает
сама.

## Трафик по клиентам и по выходам правил (0.50.0)

**Трафик в прозрачном режиме считается и без статистики xray.** Раньше строка
«Трафик» показывала только данные API xray, а если он не отвечал (например,
порт API закрыт) — строка оставалась пустой. Теперь там два источника:

- **клиенты** — по счётчикам самого роутера (nft): работает всегда, даже когда
  xray не отдаёт статистику;
- **через туннель / напрямую** — по статистике xray (когда она доступна).

**Трафик рядом с правилами маршрутизации.** В списке правил рядом с выходом
теперь видно, сколько прошло через этот выход: «↑ 12 МБ / ↓ 340 МБ». Важный
момент: xray не считает трафик по отдельным правилам маршрутизации — он считает
по выходам. Поэтому это объём **всего выхода**, а не только этого правила; так и
написано в подсказке под таблицей. Лампочка «Работает» по-прежнему показывает
именно это правило: когда и куда по нему последний раз уходил трафик.

## Выбор выхода списком, подсветка серверов реверса, чистка тегов (0.49.0)

**Выход моста выбирается списком.** В форме реверс-моста поля «Выход» и
«Интернет из туннеля» стали выпадающими списками: видно тег, адрес и порт
сервера, рядом пометка «выключен», а внизу — понятное пояснение. Вручную писать
тег больше не нужно — ошибиться не получится. Если сохранённый выход больше не
существует (сервер удалили), панель покажет это прямо в списке: «сервер не
найден (проверьте, не удалён ли он)».

**Теги приводятся к безопасному виду.** Раньше тег сохранялся как есть, и
пробелы или посторонние символы ломали и конфиг xray, и саму панель — сервер
мог «не находиться». Теперь при сохранении тег чистится: пробелы становятся
дефисом, кириллица транслитерируется («Германия 1» → `Germaniya-1`), остальные
символы заменяются на дефис.

**Серверы реверса видно сразу.** В списках серверов (и на «Статусе», и на
странице «Серверы») те серверы, которые заняты реверс-мостами, показаны
**жирным синим** — имя, тег и адрес. Под таблицей есть пояснение.

**Диагностика статистики.** На странице «Статус» появился раскрывающийся блок
«Проверка статистики трафика»: он показывает, что ответил API xray (или какую
ошибку выдал) и сколько строк со счётчиками удалось разобрать. Если столбец
«Трафик» пуст — этот блок покажет причину.

## Список различий больше не бывает пустым (0.48.0)

На странице «Конфиг» блок «Различия с файлом на роутере» мог написать «файл
отличается», а сам список различий оставался пустым: панель полагалась на формат
вывода `diff`, а он на разных сборках busybox бывает разным.

Теперь сравнение делается построчно и не зависит от `diff`:

- «в файле, но не в настройках: …» — то, что осталось от прежнего конфига
  (например, правила, которые уже удалены в панели);
- «в настройках, но не в файле: …» — то, что ещё не записано на роутер;
- если строки те же, но идут в другом порядке (поменялся порядок серверов или
  правил), так и написано — пустого поля больше не будет.

Проверено на стенде: список различий печатается и для «лишних» строк, и для
случая «те же строки в другом порядке».

## Различия, трафик и переносимый бэкап (0.47.0)

**Различия — теперь отдельным блоком на странице «Конфиг».** Раньше разница
показывалась только строчкой сверху, и её приходилось искать. Теперь на
странице «Конфиг» есть карточка **«Различия с файлом на роутере»**: либо
«различий нет — файл полностью совпадает с настройками», либо список строк (до
20) с пометкой, что есть в файле, а чего в настройках нет, и наоборот.

**Строка «изменено, но ещё не применено» больше не висит.** Она очищается сразу
при нажатии «Применить конфиг» — раньше список чистился только после того, как
фоновая задача закончит работу, и надпись оставалась на странице, хотя конфиг
уже применился.

**Трафик по серверам.** На странице «Серверы» под таблицей появилась строка
«Всего через серверы с момента последнего запуска xray: ↑ … / ↓ …». Столбец
«Трафик» у каждого сервера заполняется из статистики самого xray, поэтому
счётчики начинаются с нуля при каждом перезапуске — теперь это подписано.

**Трафик в «Прозрачном режиме».** На странице «Прокси» в таблице сверху
добавлена строка **«Трафик»**: сколько прошло через туннель и сколько напрямую
(вверх и вниз), с момента последнего запуска xray.

**Настройки стало проще переносить на другой роутер.** Список клиентов (адреса
конкретных устройств) по умолчанию **не попадает** в файл настроек — на другом
роутере такие адреса чужие. В файле он остаётся закомментированной строкой,
чтобы было видно, что было. Если сохраняешь настройки для этого же роутера —
на странице «Бэкап» есть галочка «включить в файл список клиентов». При
восстановлении панель, как и раньше, убирает из списка адреса, которых на новом
роутере нет.

## Исправлено: конфиг больше не «не записывается» (0.46.0)

Главная ошибка, из-за которой конфиг применялся «в панели», но файл на роутере
оставался старым:

- панель писала собранный конфиг во временный файл (`config.tmp.<номер>.json`),
  а перед переименованием вызывала служебные функции — и одна из них
  (обновление задач в cron) использовала **то же имя переменной** для своего
  временного файла;
- в результате панель пыталась переименовать `/etc/crontabs/root.tmp.<номер>`
  вместо конфига, получала ошибку и… в прежних версиях всё равно сообщала
  «конфиг применён». Файл на роутере не менялся: там оставался старый конфиг (а
  если файла не было — он оставался пустым), и xray не поднимался;
- проявлялось это на роутерах, где есть каталог `/etc/crontabs` (на других
  функция cron просто выходила раньше и `_tmp` не портила).

Что сделано: имя временного файла конфига теперь своё (`_cfg_tmp`), оно не
пересекается со служебными функциями. Проверено на стенде, где специально
имитируется прежняя поломка: конфиг записывается, в журнале появляется строка
«конфиг записан: … (N байт, md5 …) — совпадает с собранным».

Ещё в этой версии: сообщение про сохранённую копию конфига показывает правильный
путь (`/etc/xraypanel/config.last.json`), а ошибка переименования пишется своим
текстом, без примеси посторонних строк.

## Пустой файл конфига видно сразу (0.45.0)

Если запись конфига не сохраняется, файл может остаться **пустым** (0 байт) — и
тогда xray не запускается вообще, хотя панель «применила» конфиг. Теперь такое
видно прямо в журнале применения:

- «ВНИМАНИЕ: /etc/xray/config.json остался пустым (0 байт) — запись не
  сохранилась. Это похоже на проблему файловой системы роутера»;
- рядом печатается, где лежит собранный конфиг (`/etc/xraypanel/config.last.json`)
  и готовая команда, чтобы положить его на место руками;
- текст ошибки переименования собирается в отдельный файл, поэтому в журнал
  больше не попадают посторонние сообщения (раньше туда могло попасть
  сообщение от другой команды).

## Версия панели видна в «Статусе» (0.44.0)

На странице «Статус» в таблице состояния появилась строка **«Версия панели»** —
теперь сразу видно, какая версия стоит на роутере. Версия берётся из файла,
который ставится вместе с пакетом (`/etc/xraypanel/version`), а если файла нет —
из данных установленного пакета в opkg. Так удобнее: после обновления сразу
понятно, поставилось ли оно.

## Понятно, почему конфиг не записался, и что делать (0.43.0)

Прежняя панель писала «конфиг применён», даже если файл на роутер **не
записался**: ошибка записи уходила в никуда, а панель рапортовала об успехе.
Из-за этого казалось, что «конфиг применяется, а файл не перезаписывается».

Что теперь:

- панель проверяет результат записи и, если записать не удалось, пишет прямо:
  «ОШИБКА: не удалось записать /etc/xray/config.json: Read-only file system» (с
  настоящим текстом ошибки от системы);
- рядом пишется, доступен ли каталог конфига для записи (да/нет) — сразу видно,
  в файловой системе дело или в правах;
- **собранный конфиг сохраняется в `/etc/xraypanel/config.last.json`** (этот
  каталог обычно доступен на запись) и в журнале печатается готовая команда,
  чтобы скопировать его руками: `cp /etc/xraypanel/config.last.json /etc/xray/config.json`;
- сообщения о неудачной записи в `/etc/crontabs` больше не сыплются в журнал —
  панель просто молча пропускает эти шаги, если каталог недоступен.

Заодно исправлено: если в поле резолверов написано несколько адресов через
пробел, панель понимала их как **один** адрес — в конфиг попадала строка вида
`"9.9.9.9 1.1.1.1 8.8.8.8"`. Теперь такие адреса разбираются по отдельности.

## Видно, что конфиг действительно записан, и с каким файлом работает xray (0.42.0)

Было непонятно: панель пишет «конфиг применён», а файл в каталоге будто не
меняется. Теперь применение конфига оставляет в журнале проверяемый след:

- строка вида «конфиг записан: /etc/xray/config.json (12345 байт, md5 …) —
  совпадает с собранным». Это значит: панель действительно записала файл, и он
  ровно такой, каким его собрала;
- если после записи содержимое не совпало — панель прямо предупредит:
  «ВНИМАНИЕ: файл после записи не совпадает с собранным… возможно, файл
  подменила другая программа». Так видно случаи, когда конфиг кто-то
  перезаписывает обратно;
- после перезапуска в журнал пишется, **с каким конфигом запущена служба**:
  «служба xray запущена так: /usr/bin/xray run -config /etc/xray/config.json».
  Это отвечает на вопрос «откуда xray читает настройки»: путь виден прямо в
  команде службы.

Заодно исправлено поведение, из-за которого в журнале появлялось «в каталоге
конфига убраны лишние файлы (переименованы в .bak)»:

- панель больше **не переименовывает чужие `.json`** в каталоге конфига — там
  могут лежать файлы других программ. Про них только пишется строка «в каталоге
  конфига есть другие .json (не трогаю)»;
- убираются только собственные временные файлы панели
  (`config.tmp.<номер>.json`), и то если они остались после сбоя;
- временный файл теперь называется с номером процесса, чтобы не путаться с
  чужими `config.new.json`.

## Страница «Конфиг»: настройки сверху, файл — в свёрнутом виде (0.41.0)

Страница «Конфиг» переставлена так, как удобнее в работе:

- сверху и сразу открытым — **что получится по текущим настройкам**;
- ниже, в свёрнутом блоке — **файл на диске** (то, с чем сейчас работает xray);
- если файл отличается от настроек, панель пишет **чем именно**: показывает
  первые различия строками вида «в файле, но не в настройках: …» и «в настройках,
  но не в файле: …». Это сразу видно и «зависшие» правила, которые уже удалены
  в панели, но остались в старом конфиге;
- пустые строки и хвостовые пробелы при сравнении больше не учитываются —
  раньше из-за них панель могла ругаться на одинаковые файлы;
- на странице «Статус» добавлен **журнал применения конфига**: видно каждый шаг
  (собран конфиг → проверен → записан → xray перезапущен) или то место, где
  панель споткнулась. Если кнопка «Применить конфиг» ничего не меняет — ответ
  будет здесь.

## Видно, что именно не применено (0.40.0)

Плашку «настройки изменены» заменили на понятный список:

- в шапке, справа, появляется кнопка **«Применить конфиг»** — ровно тогда, когда
  есть что применять;
- ниже, в области объявлений (там же, где обычные сообщения), пишется, **что
  именно** изменено и ещё не вступило в силу: например «выключен сервер
  «Германия»; изменено правило: youtube.com; выключен мост «test2»»;
- список показывает последние пять пометок; если изменений больше — в конце
  дописывается «и ещё N»;
- пометки ставятся при любом изменении настроек: серверы, реверс-мосты, правила
  маршрутизации, порядок правил, выход по умолчанию, подписки, порты и папка
  журналов панели. После применения конфига список очищается;
- одинаковые пометки не копятся: если выключить и включить одно и то же,
  в списке останется одна строка;
- на странице «Конфиг» по-прежнему есть точная проверка: «файл совпадает с
  текущими настройками» или «файл отличается».

Автоматического применения нет: перезапуск xray рвёт соединения и реверс-мост,
поэтому применение остаётся осознанным действием — просто теперь всегда видно,
что именно ждёт своей очереди.

## Кнопка «Применить конфиг» везде и плашка о неприменённых изменениях (0.39.0)

Раньше конфиг применялся кнопкой только на странице «Статус», и легко было
забыть, что настройки уже изменены, а xray работает по старому конфигу:
в панели новое, в файле — старое.

Что теперь:

- кнопка **«Применить конфиг»** есть на страницах «Серверы», «Реверс»,
  «Конфиг» и «Статус» (на «Прокси» и «Маршрутах» свои кнопки применения —
  «Сохранить и включить с автооткатом» и «Подтвердить конфиг»);
- на **любой** странице сверху появляется плашка: «Настройки изменены, но в
  конфиг xray ещё не применены» — вместе с кнопкой применения. Плашка исчезает
  сразу после применения;
- на странице «Конфиг» добавлена точная проверка: «файл совпадает с текущими
  настройками» или «файл отличается — нажмите «Применить конфиг»». Там панель
  собирает конфиг заново и сравнивает с тем, что лежит на роутере;
- автоматического применения нет и не появилось: перезапуск xray рвёт
  соединения и реверс-мост, поэтому применение остаётся осознанным действием.

Как быстро узнать, нужно ли применять: если плашки сверху нет — значит, xray
работает ровно по тем настройкам, что видны в панели.

## Серверы и мосты можно выключать, а не удалять (0.38.0)

Раньше сервер или реверс-мост можно было только удалить. Теперь у каждого в
списке есть кнопка **⏸ выключить**:

- запись остаётся в панели (серым, с пометкой «выключен»), но в конфиг xray не
  попадает — как будто её нет;
- кнопка превращается в **▶ включить** и возвращает всё обратно;
- ничего не теряется: адрес, ключи, домен моста остаются на месте — удобно
  проверять узлы по одному, не пересоздавая их.

Что происходит с остальной панелью:

- выключенный сервер не участвует ни в автовыборе по пингу, ни в балансировке,
  ни в измерении задержки «выбрать лучший по пингу», и не может быть выходом по
  умолчанию;
- правила, которые указывают на выключенный сервер, в конфиг не попадают
  (в списке они видны, но не действуют) — так xray не ломается из-за ссылки на
  несуществующий выход;
- выключенный реверс-мост не прописывается ни в конфиг, ни в правила, и в списке
  показан как «выключен — в конфиг не попадает»;
- если выходом моста или правилом выбрана выключенная запись, панель подставляет
  `direct`, а не оставляет мёртвую ссылку;
- сервер, который занят реверсом, выключить нельзя — панель попросит сначала
  перевести мост на другой выход (иначе мост остался бы без туннеля).

После включения или выключения не забудьте нажать «Применить конфиг», как и для
любых других изменений.

## Строки панели идут первыми в списке dnsmasq (0.37.0)

Свои строки DNS-туннеля панель теперь ставит **в начало** списка серверов
dnsmasq, а чужие (DoH от https-dns-proxy и любые другие) — после них.

Зачем: если в dnsmasq включён строгий порядок (`strictorder`), он опрашивает
серверы сверху вниз — и тогда первыми идут резолверы панели, а DoH становится
запасным путём. Если строгий порядок выключен (это обычный режим), порядок роли
не играет: dnsmasq всё равно измеряет время ответа и выбирает быстрейшего.

Чужие строки при этом не теряются: панель запоминает их, ставит свои первыми,
возвращает остальные, а при выключении убирает только свои. Дубли не накапливаются.

## Несколько DNS-резолверов в панели (0.36.0)

Раньше у DNS-туннеля панели был ровно один резолвер: вход на 5353-м порту
жёстко смотрел на один адрес (по умолчанию 1.1.1.1). Если этот резолвер
переставал отвечать, DNS через панель просто переставал работать.

Теперь резолверов может быть несколько — до четырёх, через запятую, точку с
запятой или пробел:

    Резолверы: 1.1.1.1, 8.8.8.8, 9.9.9.9

Панель поднимает каждому свой вход туннеля — порты 5353, 5354, 5355 — и
прописывает все три строки в список dnsmasq. Дальше dnsmasq сам измеряет, кто
отвечает быстрее, и уходит на другого при сбое. Если у тебя ещё и DoH от
https-dns-proxy, он остаётся в том же списке запасным путём.

Что важно знать:

- выбор между резолверами делает **dnsmasq**, поэтому работает он в режиме
  «перехватывать DNS клиентов → в роутерный резолвер» (и у самого роутера).
  Если заворачивать клиентов напрямую в xray, они всегда попадут на первый
  резолвер из списка: правило фаервола указывает на конкретный порт;
- порты подбираются автоматически и не конфликтуют с портом перехвата трафика,
  SOCKS и API — занятые пропускаются (например, при перехвате на 5354 резолверы
  займут 5353, 5355, 5356);
- при выключении панель убирает ровно свои строки; серверы https-dns-proxy и
  любые другие остаются нетронутыми.

## Возврат серверов dnsmasq больше не «склеивает» список (0.35.0)

Была ошибка в возврате настроек. Прежняя версия панели сохраняла список
серверов dnsmasq командой `uci show`, а она печатает **все значения одной
строкой** (`server='127.0.0.1#5053' '127.0.0.1#5054'`). При выключении панель
возвращала эту строку целиком как одно значение — в настройках появлялась одна
длинная запись с кавычками, и dnsmasq её уже не понимал: серверы переставали
работать.

Что исправлено:

- список больше не сохраняется и не возвращается целиком: панель запоминает
  только значение `noresolv` и свою строку, а чужие серверы не трогает;
- если остался старый файл с «склеенной» строкой, при возврате она делится на
  отдельные значения — кавычки убираются, каждая запись встаёт на своё место;
- значения с пробелами и кавычками (то есть уже испорченные) не возвращаются
  вовсе, а из текущего списка такие записи убираются;
- список не обрастает дублями: своя строка сначала убирается и только потом
  добавляется, повторное включение ничего не копирует.

Проверка: повторное включение панели не добавляет вторую строку 5353, а
выключение возвращает чужие серверы отдельными значениями.

## DNS с запасным путём (0.34.0)

Раньше панель, переводя DNS роутера в туннель, **стирала весь список**
вышестоящих серверов у dnsmasq и оставляла только свою строку
(`127.0.0.1#5353`). Значит, откатываться было некуда: если туннель переставал
разрешать имена, DNS пропадал целиком — и у роутера, и у клиентов. Плюс при
каждом включении/выключении в список добавлялись копии строк (те самые дубли).

Что теперь:

- панель **не трогает чужие строки**. Свою строку она сначала убирает (чтобы
  не копились дубли) и добавляет заново, а серверы https-dns-proxy и любые
  другие остаются на месте. Если туннель не ответит, dnsmasq сам возьмёт ответ
  у другого сервера из списка — это и есть автоматический откат;
- при выключении убирается **только своя строка**, остальные не трогаются. Если
  список оказался пустым (так делали прежние версии панели), сохранённые
  строки возвращаются — обновление с прошлых версий безопасно;
- новая настройка «Куда заворачивать DNS клиентов»:
  - **в xray** — как раньше: запросы клиентов уходят прямо в туннель;
  - **в роутерный резолвер** — запросы попадают на dnsmasq, и он сам решает,
    куда их отправить. Тогда клиенты получают тот же откат на DoH, что и сам
    роутер. Этот режим ловит и устройства с жёстко прописанным DNS
    (например, `8.8.8.8`): их запросы всё равно приходят на роутер.

Важно для отката: в списке у dnsmasq должны остаться рабочие серверы (DoH от
https-dns-proxy или обычный DNS). Если там только строка туннеля, откатываться
будет не на что — это уже дело настроек самого роутера.

## Две отдельные галочки для DNS (0.33.0)

Раньше одна галочка «DNS через туннель» делала сразу две разные вещи:
перехватывала запросы клиентов (правила фаервола на 53-й порт) и переводила на
тот же путь dnsmasq самого роутера. Из-за второй части панель и
https-dns-proxy спорили за один общий список серверов в настройках dnsmasq:
панель при включении стирала все строки и оставляла только свой адрес
(`127.0.0.1#5353`), а прокси прописывал свои. Кто записал последним — тот и
работал, а после нескольких включений в списке копились дубли.

Теперь это две независимые галочки:

- **перехватывать DNS клиентов** — только правила фаервола: запросы клиентов
  из списка уходят в туннель, dnsmasq при этом не трогается;
- **и DNS самого роутера (dnsmasq)** — переводит на тот же путь уже сам
  роутер. Выключено — dnsmasq остаётся со своими вышестоящими серверами
  (например, с https-dns-proxy).

Если новая галочка не задана (установка обновляется), панель ведёт себя как
раньше: одна галочка включает и то, и другое. Ничего перенастраивать вручную
после обновления не нужно.

Зачем: теперь можно держать у роутера свой DoH (https-dns-proxy), а панелью
заворачивать DNS только у выбранных клиентов — и наоборот.

## Видно, что правила вернулись после перезагрузки (0.32.0)

Строка «Последний запуск» на странице прозрачного режима могла вводить в
заблуждение: при выключении роутера правила снимаются штатно, и панель
записывала «правила сняты, трафик идёт как обычно». После загрузки правила
возвращались, а эта запись оставалась на месте — выглядело так, будто режим
не работает, хотя перехват уже стоял.

Что теперь:

- при автозагрузке строка обновляется: «правила восстановлены автоматически,
  автооткат не нужен» — и рядом с ней видно время;

Сама логика не изменилась: правила по-прежнему ставятся при загрузке, если
режим включён в настройках.

## Обновление списков из интернета (0.30.0)

В блоке «Готовые списки (гео)» появилось обновление файлов прямо из панели —

В журнале обновления (спойлер под кнопкой) видно каждый шаг: что скачано,
сколько названий нашлось, куда положено. Если скачать не удалось — прежние

## Проверка домена показывает и перекрытые правила (0.28.0)

Проверка домена теперь отвечает на вопрос «почему моё правило не ловит»: она
показывает не только первое подходящее правило, но и те, что ниже и перекрыты:

```
Домен: www.vk.com
Есть в готовых списках: VK, MAILRU, MAILRU-GROUP, CATEGORY-RU, GEOLOCATION-!CN, …
Работает правило: r1 — geosite:category-ru → direct
Ниже подходят, но перекрыты этим правилом:
   перекрыто: r2 — domain:vk.com → 🇩🇪frankfurt
(xray берёт первое подходящее сверху — чтобы работало своё правило, поднимите его кнопкой ⤒)
```

Это самая частая причина «правило по домену не работает»: выше него стоит
широкий список (например `geosite:category-ru` или `geosite:ru`), который
подходит первым и забирает трафик. Сами правила `domain:`, `full:` и `keyword:`
рабочие — это проверено на обеих версиях xray (24.12.31 и 26.7.28).

Вторая причина, по которой правило по домену не сработает: xray не увидел имя
сайта в соединении (например, приложение ходит прямо по адресу или не по
TLS/HTTP). Тогда помогают только правила по адресам (`geoip`). В столбце
«Работает» это видно: в скобках будет адрес, а не имя.

## Подбор правила для домена, как в PassWall (0.27.0)

На странице «Маршруты» появился блок **«Подобрать правило для домена»**. Вводите
домен (можно с `www`, можно вставить ссылку целиком) и нажимаете «проверить
домен». Панель читает файлы со списками на роутере и отвечает:

- **в каких готовых списках этот домен есть** — например для `www.youtube.com`:
  `YOUTUBE, GOOGLE, CATEGORY-COMPANIES, GEOLOCATION-!CN, ALPHABET,
  CATEGORY-ENTERTAINMENT`;
- **какое ваше правило его поймает** — с учётом порядка правил (первое
  подходящее сверху), например «r1 — `domain:youtube.com` → direct»;
- **что делать, если не ловит ни одно** — панель подскажет список, который стоит
  взять: для `ozon.ru` это `OZON`, а не общий `CATEGORY-RU`.

Заодно по делу отвечает на вопрос «почему видео уходит по другому правилу»:
проверка `r5---sn-x.googlevideo.com` покажет, что под правило
`domain:youtube.com` он не подходит (это не поддомен youtube.com), а в списке
`YOUTUBE` он есть — значит и ловить его надо списком.

Проверка идёт пару секунд (читает файл со списками), результат запоминается: тот
же домен в следующий раз проверяется мгновенно.

## Видно, что именно поймало каждое правило (0.26.0)

В столбце «Работает» на странице «Маршруты» теперь показываются до трёх адресов,
которые правило реально поймало, с количеством соединений: например

Это снимает главную путаницу с правилами по домену. Пример: правило

## Лампочки у правил: видно, какое правило работает (0.20.0)

- Если файлы обновились после сбора (или какой-то из них появился позже),
  панель собирает названия заново сама: сравнивает размер и время файлов с
  теми, что были при сборе. Журнал сбора теперь видно всегда, а не только когда
  список пуст.

## Подсказка похожих названий (0.19.2)

Если введённого названия списка нет, панель теперь показывает похожие — те, в
которых встречается введённый текст. Так сразу видно, что писать вместо,
например: на «ru» отвечает «нет такого списка. Похожие названия:
category-ru, category-bank-ru, autoru …».

Заодно из официальных списков v2fly видно важное: списка с именем ровно `ru`
для доменов не существует. Российские домены лежат в списке `category-ru`
(в нём же все домены `*.ru`), а российские адреса — в списке адресов `ru`
(`geoip:ru`). Названия нужно брать из подсказки в поле значения: панель
показывает только те, что реально есть в файлах роутера.

## Исправление в 0.19.1

Проверка названия списка («проверить название» на странице «Маршруты») отвечала

темах.

## Почему журнал xray показывал время UTC

OpenWrt хранит часовой пояс в `/etc/TZ` — его читают busybox и LuCI, поэтому
сам роутер живёт по местному времени. А xray написан на Go, и Go смотрит только
на `/etc/localtime`. Если этого файла нет, служба пишет время по UTC.

Лечится кнопкой «Выставить журналу время роутера» на странице «Статус»: она
ставит ссылку `/etc/localtime -> /usr/share/zoneinfo/<пояс роутера>` и
перезапускает xray. Старые записи в журнале останутся в UTC, новые пойдут по
местному времени.

Если панель сообщает, что файла зоны нет, значит на роутере не установлены
данные часовых поясов: панель подскажет точную команду (`opkg install
zoneinfo-europe` для Europe/Berlin, `zoneinfo-asia` и так далее). После
установки достаточно нажать кнопку снова.

## Исправление проверки реверсов (0.4.11)

В версии 0.4.10 проверка искала сервер не по тому тегу: брался тег моста, а не
тег сервера из поля «Выход». Из-за этого живое соединение никогда не находилось
и решение принималось только по свежести записей в журнале — поэтому все мосты
могли разом покраснеть, хотя работали.

Теперь порядок такой:

1. есть ли у роутера живое TCP-соединение с сервером, указанным у моста
   в поле «Выход» — если да, мост зелёный;
2. если нет — насколько свежая последняя запись этого моста в журнале xray
   (окно 5 минут).

Причина пишется в столбце «Состояние»: «соединение с <адрес>:<порт> есть»,
«нет соединения с <адрес>:<порт>», «последняя активность N мин назад».

## Как определяется живой реверс

Две проверки, по очереди:

1. время последней записи этого моста в журнале xray. Мост постоянно шлёт
   служебные сообщения (примерно раз в 30 секунд), поэтому если последняя
   запись старше 5 минут — мост считается отвалившимся;
2. если журнала нет вообще — панель смотрит, есть ли установленное TCP-соединение
   с сервером, указанным у моста в поле «Выход».

Окно в 5 минут выбрано специально: сразу после обрыва записи могут ещё
оставаться свежими, поэтому цвет меняется не мгновенно, а спустя несколько
минут — чтобы не мигало из-за коротких переподключений.

## Список клиентов — из постоянных аренд DHCP

Список для галочек берётся из постоянных аренд DHCP роутера
(LuCI → Сеть → DHCP и DNS → Статические аренды). Таблица ARP для этого больше
не используется: она тянула лишние адреса (сам роутер, промежуточные
устройства). Если постоянных аренд нет вообще, панель покажет текущие выданные
адреса и подскажет, где задать постоянные. Устройства, которых нет в списке,
выбрать нельзя — это и есть нужное поведение.

## Выход по умолчанию — зачем он

Это выход для трафика, который не попал ни под одно правило: клиенты SOCKS-входа
панели (10808), прозрачный режим в варианте «по правилам панели» и всё прочее
без явного маршрута. Реверс-мосты и правила маршрутизации его не используют,
а при включённом автовыборе по пингу он не участвует вовсе. Если оставить поле
пустым, такой трафик идёт напрямую.

## Выбор клиентов галочками

На странице «Прозрачно» клиенты из аренды DHCP отмечаются галочками (имя, адрес,
MAC). Поле «Дополнительно» показывает только те адреса, которых нет в списке
аренды, поэтому отмеченные галочками адреса там не дублируются.

## Серверы реверса не участвуют в выходе

Сервер, указанный в реверс-мосте («Выход»), — это вход туннеля, а не выход в
интернет. Такой сервер:

- не показывается в списке «Куда направлять» на странице «Прозрачно»;
- не попадает в автовыбор по пингу (балансировщик и observatory);
- пропускается кнопкой «Выбрать лучший по пингу» (в отчёте пишется, что он
  занят реверсом).

Так исключается возврат трафика на роутер: раньше, если выбрать такой сервер
выходом, трафик уходил в туннель, возвращался на роутер и выходил через его
собственный интернет.

## Что значит лог доступа xray

- `[transparent -> <тег>]` — перехваченный трафик клиента ушёл через этот
  выход. По этой строке видно, какой сервер реально используется;
- `[reverse-1 -> direct]` и подобное — трафик, который пришёл по реверсу от
  нашего сервера, выпускается напрямую через интернет роутера. Это и есть
  режим «клиент видит внешний адрес роутера»;
- подключения к адресу портала (`...:54781`) в перехват больше не попадают:
  адреса серверов из списка исключаются из правил, иначе сам реверс зависел бы
  от выбранного сервера-выхода.

Портал реверса (наш сервер) как «выход» использовать нельзя: трафик уходит в
туннель, возвращается на роутер и выходит через его интернет. Настоящий выход
меняет адрес на адрес соответствующего сервера.

## Выбор клиентов и выход «по пингу»

- клиенты выбираются в списке (можно отметить несколько, Ctrl или Shift) там же,
  где раньше было поле адресов; повторное включение просто обновляет выбор,
  адреса больше не дублируются. Поле «Дополнительно» — для адресов, которых нет
  в аренде DHCP;
- в списке «Куда направлять» есть пункт «по лучшему пингу (авто,
  балансировщик)». Он включает режим автовыбора: xray сам проверяет серверы и
  берёт самый быстрый. Это тот же режим, что галочка в «Настройках»;
- страница «Прозрачно» обновляется раз в 15 секунд, и только пока идёт
  включение/выключение или тикает автооткат — в обычном состоянии она стоит
  на месте, и текст можно спокойно скопировать.

## Правила ставятся только после успешного применения конфига

Включение прозрачного режима идёт одной операцией
(`transparent-enable.sh`): сначала применяется конфиг xray и перезапускается
служба, и только если это прошло успешно — ставятся правила фаервола.
Если конфиг не принят, правила не ставятся вообще: иначе трафик завернулся бы
в порт, который никто не слушает, и у клиентов пропал бы интернет.

Причина неудачи пишется в «Последний запуск» на странице «Прозрачно» и в
журнал (последние 20 строк).

## Тонкости nftables, которые уже учтены

- для перенаправления порта nft требует явного указания протокола, иначе
  «transport protocol mapping is only valid after transport protocol match» —
  поэтому правила идут как `meta l4proto tcp redirect to :12345`;
- `fwd` — зарезервированное слово nft, цепочку с таким именем создать нельзя,
  поэтому цепочка называется `fw`;
- обязательные правила (исключения локальной сети, метка xray, перенаправление)
  при ошибке откатывают всё и пишут точную причину; необязательные
  (блокировка QUIC) только пишут предупреждение в журнал.

## Выбор клиентов галочками

На странице «Прозрачно» есть список клиентов из аренды DHCP (`/tmp/dhcp.leases`):
имя, адрес и MAC. Отмечаете галочками нужные — они попадают в список
заворачиваемых. Работает в режиме «только адреса из списка»; рядом можно
дописать адреса руками. Выход выбирается списком (теги серверов или `direct`).

Журналы прямо в панели: «Прозрачно» → «Журнал прозрачного режима» (последние
20 строк, с каждой командой nft и текстом ошибки), «Статус» → «Последнее
применение конфига» и «Последний перезапуск xray».

## Если адрес в браузере не меняется

Две самые частые причины:

1. Не выбран выход — смотрите строку «Куда уходит трафик» в блоке «Состояние».
2. Браузер ходит по QUIC (UDP 443) — он не заворачивается, поэтому сайты
   видят домашний адрес. Теперь для завёрнутых клиентов QUIC блокируется,
   и браузер сам переходит на обычный TCP через прокси.

Блок «Проверка» на странице «Прозрачно» показывает: какие мосты есть на
роутере (в настройках должен быть тот же, обычно `br-lan`), какие правила
стоят сейчас, и что попадало в перехватчик. Если журнал перехватчика пуст —
трафик до xray не доходит, обычно из-за неверного имени моста.

## Почему кнопки отвечают мгновенно

Любая тяжёлая операция (проверка конфига xray, перезапуск службы, правила
фаервола) сначала отдаёт браузеру ответ, а уже потом выполняется в фоне.
Иначе uhttpd успевает оборвать CGI по таймауту и в браузере появляется
«Bad Gateway / The process did not produce any response», хотя настройки
при этом применяются.

Результат видно на страницах: «Статус» → блоки «Последнее применение конфига»
и «Последний перезапуск xray», «Прозрачно» → блок «Журнал прозрачного режима».

## Прозрачный режим

Страница «Прозрачно». Включается кнопкой, правила фаервола панель пишет сама
(nftables, а на старых сборках — iptables). Что заворачивается:

- вся локальная сеть с выбранного интерфейса (`br-lan` по умолчанию);
- только сам роутер;
- только адреса из списка (по одному или через запятую);
- роутер и сеть вместе.

Куда направлять — тег сервера, либо пусто (тогда работают обычные правила
маршрутизации панели). Локальная сеть, сам роутер и соединения самого xray
исключаются автоматически: у соединений xray ставится метка 255, и такие
пакеты правила пропускают, иначе получилась бы петля.

Главное про безопасность: правила ставятся с автооткатом на 2 минуты. Если
после включения всё работает — нажмите «Подтвердить», правила останутся.
Если не нажать (например, роутер остался без интернета), они снимутся сами.
Выключить в любой момент — кнопка «Снять правила и выключить».

После перезагрузки роутера правила ставятся заново автоматически, если режим
включён (init-скрипт `xraypanel-transparent`).

Ограничения версии 0.3.0: заворачивается только TCP. DNS и UDP идут как обычно
через роутер — для обычного сёрфинга этого достаточно, домены определяются по
SNI/HTTP. UDP-режим (TPROXY) планируется отдельно.

## Почему ответ приходит сразу, а xray перезапускается «в фоне»

Сначала панель отдаёт браузеру готовый ответ, и только потом перезапускает xray.
Так сделано специально: если ждать перезапуск внутри CGI, uhttpd убивает процесс
по таймауту и в браузере появляется «Bad Gateway / The process did not produce
any response», хотя конфиг уже применён. Результат перезапуска видно на странице
«Статус» в блоке «Последний перезапуск xray».

## Клиент по реверсу выходит в интернет через роутер

У моста два разных направления:

- «Выход» — через какой сервер роутер сам подключается к порталу;
- «Интернет из туннеля» — куда уходит трафик клиента, пришедшего по реверсу.
  Значение `direct` (по умолчанию) означает «через интернет самого роутера»:
  такой клиент будет видеть во внешнем мире адрес роутера.

Проверка с сервера (пока туннель поднят):

    curl -s --socks5 127.0.0.1:10809 https://api.ipify.org

Должен вернуться внешний адрес роутера, а не адрес сервера.

## Удаление

    opkg remove xraypanel

Настройки (`/etc/config/xraypanel`) при удалении сохраняются.

## Требования

- OpenWrt / ImmortalWrt 23.05 (или новее);
- установленный `uhttpd` (есть вместе с LuCI);
- xray (пакет `xray-core` или совместимый) и его init-скрипт `/etc/init.d/xray`.

## Важно про версию xray

Реверс-мосты (`reverse.bridges`) — это «старый» механизм реверса. Он работает
на xray до версии 25. В xray 25 и новее старая схема реверса удалена, и
понадобится уже новая (VLESS Reverse). Панель версии 0.1.x рассчитана на
текущий роутер (xray 24.12.31), поэтому:

- на роутере с xray 24.x всё работает как есть;
- если в виртуалке окажется xray 25/26 — реверс через панель работать не будет,
  нужно либо поставить xray 24.12.31, либо ждать версии панели с новой схемой.

## Что планируется дальше

## DNS через туннель (0.5.0)

На странице «Прозрачно» появился блок «DNS через туннель». Включаете галочку —
и запросы клиентов на 53-й порт (UDP) перехватываются на роутере и уходят через
выбранный сервер. Смысл: трафик и так идёт через туннель, а теперь и запросы имён
тоже — местный провайдер не видит, какие сайты вы открываете.

Как это сделано:

- в конфиг xray добавляется вход `dns-tunnel` (dokodemo-door, UDP, TPROXY),
  который принимает перехваченные запросы и отдаёт их в маршрутизацию;
- в фаервол добавляется цепочка `dns` в prerouting (приоритет mangle) с правилом
  `udp dport 53 tproxy to :5353`, плюс служебные правила: политическая
  маршрутизация (`ip rule fwmark 83 table 83` и `ip route local ... dev lo`);
- куда уходит DNS, определяется полем «Выход для DNS» (по умолчанию — как у
  прозрачного режима).

Работает в режимах «вся локальная сеть», «только адреса из списка» и «роутер и
сеть». Отключается снятием галочки или кнопкой «Снять правила и выключить»;
вместе с правилами снимается и политическая маршрутизация.

Если после включения что-то не открывается — не подтверждайте правила, через
5 минут они снимутся сами.

## Несколько интерфейсов и сеть WAN (0.5.1)

В поле «Интерфейсы сети» (страница «Прозрачно») теперь можно перечислить
несколько интерфейсов через запятую или пробел, например:

    br-lan wan

Тогда в правилах получается `iifname { "br-lan", "wan" }` — заворачивается и
локальная сеть, и трафик, приходящий с WAN. Это нужно, когда:

- роутер стоит за другим роутером (двойной NAT) и вы хотите завернуть клиентов
  верхней сети;
- клиенты подключаются через VPN на отдельном интерфейсе;
- есть гостевая сеть или VLAN на своём интерфейсе.

Осторожно с WAN: через ваш туннель смогут ходить все, кто может достучаться до
роутера с этой стороны (например соседи по верхней сети). Для домашнего роутера,
который сам является клиентом провайдера, WAN обычно не нужен.

## Исправления автоотката (0.5.2)

По журналу были видны три огреха, все устранены:

1. таймер автоотката от **прошлого** включения мог снять правила нового
   включения (в журнале это выглядело как «правила сняты» через полминуты

3. при снятии правил nft ругался «No such file or directory», если таблица уже
   удалена — выглядело как ошибка в журнале. Теперь удаляем только то, что
   реально есть.

Плюс убрано дублирование адресов в строке «адреса серверов не заворачиваем»
(если два сервера указывают на один IP, он теперь печатается один раз).

## Диагностика DNS-перехвата (0.5.6)

В блоке «Проверка» на странице «Прозрачно» теперь видно состояние маршрутизации
для TPROXY:

    Маршрутизация для DNS (TPROXY)
    правило: ... (fwmark 83 -> таблица 83)
    маршрут: local default dev lo

Если там «НЕТ» — перехваченные DNS-запросы не доходят до xray и умирают: снаружи
это выглядит как «DNS не отвечает» (а если провайдер блокирует внешний DNS,
то и как таймаут). Скрипт теперь пишет об этом в журнал прозрачного режима и
пробует два варианта синтаксиса `ip` (busybox понимает и `lookup`, и `table`).

Проверить руками на роутере:

    ip rule show | grep 83
    ip route show table 83

## Перехват DNS по TCP тоже (0.5.7)

Раньше перехватывался только UDP/53: клиент, обратившийся к DNS по TCP (так бывает
при больших ответах или при явном `+tcp` в dig), уходил в общий прозрачный режим —
а он отправлял запрос на исходный адрес (роутер), и через туннель тот был
недостижим. Теперь в цепочке `dns` два правила — `udp dport 53` и `tcp dport 53`,
оба ведут в `dns-tunnel`, а сам вход слушает `network: tcp,udp` с
`followRedirect: false` (то есть запрос идёт строго на указанный резолвер).

Важно: отдельное правило маршрутизации для входа `dns-tunnel` не нужно — он
специально отпускается в общий маршрут (балансировщик или выход по умолчанию).
Правки dnsmasq (`noresolv`, `server=127.0.0.1#5353`) для этой схемы тоже не нужны:
xray не предоставляет DNS-сервер, перехват делает фаервол до dnsmasq.

## UDP-DNS отдаём внутреннему резолверу xray (0.5.8)

Проверка показала: UDP-запросы доходят до сервера, но ответы не возвращались к
клиенту — проксирование UDP-пакета через туннель в этом сценарии ненадёжно.
Теперь сделано по штатной схеме xray:

- в конфиг добавляется секция `dns` с тегом `dns-out` и вашим резолвером;
- перехваченные запросы клиентов (`dns-tunnel`) отдаются этому резолверу —
  xray сам формирует ответ и возвращает его клиенту (проверено на живом xray:
  ответ возвращается сразу);
- собственные запросы резолвера к внешнему серверу идут через выбранный
  «Выход для DNS» (или через общий маршрут, если поле пустое).

Заодно исправлено накопление правил: повторное включение режима больше не
добавляет дубли `ip rule`, а выключение убирает все, даже оставшиеся от
прошлых включений.

Попутно: пакет 0.5.7 был собран правильно (внутри лежит нужный скрипт), поэтому
если после установки файлы не меняются — стоит проверить, тот ли файл копируется
на роутер (хеш `transparent.sh` в пакете 0.5.7: c9a2532c4cd3334a0d90bc26682b0986).

## Сохранение и восстановление настроек + DNS на старых сборках xray (0.16.2)

Сохранение настроек:

- на странице «Бэкап» кнопка «Скачать настройки» отдаёт файл со всем
  содержимым `/etc/config/xraypanel`;
- рядом — «Восстановление настроек»: выбираете файл в проводнике, панель
  сама разбирает загруженный файл (multipart/form-data) и применяет его;
- перед записью прежний конфиг сохраняется рядом как
  `/etc/config/xraypanel.bak-<дата-время>`, при ошибке в файле панель
  возвращает прежний;
- внизу остался запасной вариант «вставить текстом» — на случай, если файл
  выбрать не получается.

DNS-режимы:

- по умолчанию перехваченный DNS отдаётся внутреннему резолверу xray
  (`dns` + `outboundTag: dns-out`);
- если сборка xray этого не умеет (в журнале `non existing outTag: dns-out`,
  и запросы уходили бы мимо туннеля с утечкой), панель при применении конфига
  сама переключается на режим «пересылать через выбранный сервер» и пишет об
  этом в журнал применения;
- режим виден на странице «Прозрачно» и переключается вручную в поле
  «Как выпускать DNS».

Попутно исправлено: вставка настроек текстом больше не теряет переводы строк
(`%0A` в старом разборе съедался подстановкой команды).

## Починка перехвата DNS: ответ не доходил до клиента (0.16.2)

Нашли настоящую причину, почему перехваченный DNS «не работал», хотя всё
остальное было исправно:

- запрос клиента перехватывался, уходил в туннель, доходил до сервера,
  1.1.1.1 отвечал, ответ возвращался на роутер — это видно и в журнале xray
  на роутере, и в tcpdump на сервере;
- но xray отдавал ответ клиенту **со своего порта 5353**, а клиент ждёт ответ
  с того адреса, куда сам спрашивал (`192.168.11.1:53`). Такой ответ ядро
  клиента просто выбрасывает, и `dig` уходит в таймаут, хотя ответ был.

Проверка, которая это показала: сокет в клиенте, не привязанный к адресу
отправителя, показал `ОТВЕТ от ('192.168.11.1', 5353)` вместо порта 53.

Как исправлено: перехват DNS переведён с TPROXY на обычный `redirect` (DNAT)
в nat-цепочке `dns` (priority -110). Теперь conntrack сам подменяет адрес
отправителя ответа обратно на исходный — так же, как это уже работает для
обычного прозрачного трафика. Правила TPROXY (`ip rule`/таблица 83) больше не
нужны и снимаются при включении режима.

Заодно:

- режим «пересылать через выбранный сервер» стал значением по умолчанию
  (внутренний DNS-выход `dns-out` на xray 24.12.31 не работает — в журнале
  видно `non existing outTag: dns-out`);
- переключатель «Как выпускать DNS» снова работает в обе стороны: выбор
  «внутренним резолвером xray» сохраняется явно и не перебивается значением
  по умолчанию;
- в блоке «Проверка» вместо маршрутизации TPROXY показываются действующие
  правила перехвата DNS.

## Перенос настроек на другой роутер (0.16.2)

Список клиентов прозрачного режима хранится в настройках как адреса устройств
(`option transparent_clients`). При переносе файла на другой роутер там может
не быть этих устройств — адрес остаётся в настройках, правило в фаерволе
создаётся, но ни на кого не срабатывает.

Теперь при восстановлении настроек панель сверяет список с тем, что реально
есть на этом роутере (постоянные аренды DHCP + текущие выданные адреса),
убирает лишние и пишет об этом в сообщении: «Из списка клиентов убраны адреса,
которых на этом роутере нет: …». Если своих адресов не осталось, настройка
удаляется целиком.

## Выбор интерфейсов списком и надёжное определение моста (0.16.2)

- Поле «Интерфейсы сети» больше не текстовое: интерфейсы выбираются списком
  (можно отметить несколько — например `br-lan` и `wan`). Рядом осталось поле
  для ручного ввода, если нужного интерфейса в списке нет; выбранное и
  вписанное объединяется, повторов не будет.
- Список интерфейсов определяется по ядру (`/sys/class/net/<имя>/bridge`) и по
  конфигурации сети OpenWrt, а не только командой `ip link show type bridge`.
  Это важно на роутерах, где `ip` урезанный (busybox) и такая команда молчит:
  из-за этого после переноса настроек панель могла писать, что мост не найден,
  хотя он есть.
- Проверка моста в панели теперь сравнивает список настроенных интерфейсов с
  найденными и красным предупреждает только тогда, когда совпадений нет
  совсем. Если определить не удалось — панель подсказывает посмотреть имена
  командой `ls /sys/class/net` и выбрать нужный интерфейс списком.

## Выпадающий список интерфейсов и разбор «вход не поднялся» (0.16.2)

- Интерфейс сети теперь выбирается выпадающим списком (а не списком с
  прокруткой). Дополнительные интерфейсы, если их нужно несколько, вписываются
  в поле рядом — например `wan`. Выбранное и вписанное объединяется.
- Если после переноса настроек вход перехвата не поднялся (панель писала
  «порт 12345 не слушает: xray не поднял вход»), теперь прямо под таблицей
  состояния показываются последние строки журнала применения конфига и журнала
  ошибок xray — по ним сразу видно причину.
- При восстановлении настроек панель убирает настройки, которые годятся только
  для прежнего роутера: путь к бинарнику xray, путь к конфигу, каталог
  журналов и имя службы — если на этом роутере таких файлов нет. Иначе панель
  искала бы xray там, где его нет, и вход перехвата не поднимался бы, хотя
  сам xray на роутере установлен.

## Служба xray выключена в OpenWrt (0.16.2)

На новом роутере панель писала «xray НЕ поднялся», конфиг при этом был
правильный (`xray run -test` → `Configuration OK`), а `ps` не показывал
процесса. Причина оказалась в настройках самого OpenWrt: в `/etc/config/xray`
стоит `enabled='0'`, то есть служба выключена. В этом случае
`/etc/init.d/xray restart` ничего не делает, procd показывает пустой список
экземпляров, и xray не запускается — хотя и бинарник, и конфиг в порядке.

Что сделано:

- панель сама включает службу, если видит `enabled='0'`, и пишет об этом в
  журнал применения конфига;
- на странице «Прозрачно», если вход перехвата не поднялся, панель прямо
  говорит, что служба xray выключена, и показывает команду для ручного
  включения.

Вручную это делается так:

    uci set xray.enabled.enabled=1; uci commit xray; /etc/init.d/xray restart

## Установка xray вместе с панелью и проверки безопасности (0.16.2)

Панель — это только управление: без установленного xray она бесполезна, а
раньше об этом молчала. Теперь:

- при установке пакета postinst проверяет, есть ли xray. Если он уже стоит —
  ничего не устанавливается, панель просто работает с ним. Если нет — в фоне
  доставляется пакет `xray-core` (журнал `/etc/xraypanel/install.log`),
  включается автозапуск службы, собирается конфиг панели и запускается xray;
- если xray уже запущен с конфигом другой программы, установщик его не
  перезаписывает: в журнале появится запись, что панель ждёт, пока вы сами
  нажмёте «Применить конфиг»;
- чужой конфиг в каталоге сохраняется: перед первой перезаписью делается копия
  `/etc/xray/config.json.bak-<дата>` (и такая же копия — при применении
  конфига из панели). Свой конфиг панель узнаёт по служебному входу
  `local-access`;
- кнопки установки в панели нет: всё делает установщик, а при отсутствии xray
  на «Статусе» остаётся предупреждение с журналом установки;
- при применении конфига панель тоже проверяет наличие xray и пересобирает
  конфиг уже после установки;
- в каталоге конфига лишние `*.json` (кроме самого конфига) переименовываются
  в `.bak-<дата>`: xray запускается с `-confdir` и читает оттуда все файлы
  подряд, поэтому посторонние файлы там только мешают;
- служба xray включается и в настройках OpenWrt, и на автозапуск
  (`/etc/init.d/xray enable`).

Проверки безопасности, которые добавились:

- значения портов из формы теперь проверяются (только 1–65535), мусор не
  сохраняется — раньше он попадал прямо в конфиг xray;
- загружаемый файл настроек читается с ограничением 1 МБ, чтобы не забивать
  `/tmp`;
- на странице «Статус» появляется предупреждение, если у панели не задан
  пароль: панель работает от имени root, и без пароля её может открыть любой,
  у кого есть доступ к роутеру по сети;
- правило-«пропуск» для DNS-цепи в фаерволе теперь опирается на признак
  `ct status dnat`, а не на номер порта: раньше клиент мог обойти туннель,
  просто обратившись к любому хосту на порт 5353.

## Режим «роутер и сеть»: исправлен приоритет цепочки output (0.16.2)

В режимах «только сам роутер» и «роутер и сеть» панель создаёт цепочку для
своего же трафика, и nft её не принимал:

    nft add chain ip xraypanel out { type nat hook output priority dstnat ; }
    Error: invalid priority expression value in this context

Причина в том, что имя приоритета `dstnat` для хука `output` этот nft не
понимает (в `prerouting` оно работает). Теперь приоритет задаётся числом:

    nft add chain ip xraypanel out { type nat hook output priority -100 ; }

`-100` — то же самое, что `dstnat`, но записано так, как понимает nft на
роутере. Из-за этой ошибки правила откатывались, и режимы «только роутер» и
«роутер и сеть» не включались.

## Интерфейс в настройках не подменяется сам (0.16.2)

В выпадающем списке «Интерфейс сети» был неприятный эффект: если сохранённое
значение не совпадало со списком найденных интерфейсов, браузер сам подставлял
первый пункт списка — и в настройках оказывался, например, `eth0` (WAN), хотя
выбирали мост. Теперь в таком случае первым пунктом идёт явное «оставить как
есть», и ничего не меняется без вашего выбора.

Заодно поправлено предупреждение о несовпадении: панель пишет и то, какие
мосты она видит, и то, что стоит в настройках, а если в настройках указан
интерфейс верхней сети (`eth0`, `wan`, `eth1`) — отдельно предупреждает, что
через туннель пойдёт трафик всей верхней сети.

Напоминание по порядку действий: после «Включить с автооткатом» нужно дождаться
кнопки «Подтвердить» в блоке «Состояние» и нажать её. Если не нажать за 5
минут, панель снимет правила сама — это защита от потери доступа. Кнопка
«Снять правила и выключить» снимает правила сразу, ей пользоваться не нужно,
если вы просто хотите, чтобы режим работал.

## Режим «только сам роутер»: DNS роутера тоже через туннель (0.16.2)

Раньше перехват DNS висел только на входном трафике (LAN), а запросы самого
роутера идут мимо этого места — в цепочку `output`. Поэтому в режиме «только
сам роутер» DNS роутера уходил напрямую провайдеру, и проверка утечки из
терминала показывала чужой резолвер.

Теперь для режимов «только сам роутер» и «роутер и сеть» создаётся отдельная
цепочка `dnsout` (`type nat hook output priority -110`), которая заворачивает
запросы самого роутера на 53-й порт в туннель — UDP и TCP. Проверять утечку
можно прямо с роутера, например:

    nslookup -type=txt whoami.ds.akahelp.net

(если установлен `dig` — `dig +short TXT whoami.ds.akahelp.net`): в ответе будет
виден резолвер, который снаружи видит запрос. Должен быть наш туннель
(1.1.1.1 / наш сервер), а не провайдер.

Заодно панель перестала требовать интерфейс сети в режиме «только сам роутер»:
там он не используется, и предупреждение о несовпадении с `br-lan` больше не
показывается — вместо него пояснение, что режим работает через цепочку
`output`.

## DNS роутера — через dnsmasq, а не через правила (0.16.2)

Попытка завернуть DNS самого роутера правилами (цепочка `output` с redirect)
не работает, и это видно по журналам: запросы доходят до xray
(`accepted udp:1.1.1.1:53 [dns-tunnel -> Germ_test]`), ошибок нет, а резолвер
ответ не получает. Причина в самом механизме: пакет создаётся локально, DNAT
делает адресом назначения локальный адрес, и ответ уходит с адреса xray
(`127.0.0.1:порт`), а не с того адреса, куда резолвер спрашивал — поэтому
dnsmasq молча выбрасывает ответ.

Правильное решение (сделано вместо этого):

- при включении прозрачного режима с перехватом DNS панель переводит dnsmasq
  на локальный порт xray: `option noresolv '1'` и `list server '127.0.0.1#5353'`;
- тогда обмен идёт обычным образом по петле: роутер → dnsmasq → xray → туннель,
  ответ возвращается штатно, без подмены адресов;
- прежние настройки dnsmasq сохраняются в `/etc/xraypanel/dnsmasq.saved` и
  возвращаются при выключении режима (в том числе при автооткате).

Проверка утечки из терминала роутера теперь должна показывать наш резолвер:

    nslookup -type=txt whoami.ds.akahelp.net

Мелкая оговорка: пока режим включён, весь DNS на роутере идёт через xray —
если xray не запустится, имена перестанут разрешаться. Выключение режима
(или автооткат через 5 минут) возвращает dnsmasq как было.

## Интерфейс сети определяется сам (0.16.2)

Интерфейс локальной сети больше не выбирается руками — панель берёт его из
настроек роутера (`network.lan.device`, обычно `br-lan`) и подставляет при
включении режима. Логика простая:

- «вся локальная сеть» и «роутер и сеть» — интерфейс подставляется сам;
- «только адреса из списка» — правила работают по адресам клиентов, интерфейс
  не нужен;
- «только сам роутер» — правила работают в цепочке `output`, интерфейс тоже
  не нужен.

На странице «Прозрачно» в поле интерфейса теперь просто показано, что
определилось. Ручное поле остаётся только на случай, если определить не
удалось (например, на нестандартной сборке) — тогда панель попросит вписать
мост. Длинная подсказка про перечисление нескольких интерфейсов через запятую
убрана: она больше не нужна.

## Оформление панели: шесть тем (0.16.2)

Появился выбор оформления — не только цветов, но и расположения: где меню,
насколько плотные списки, какие кнопки. Выбирается на странице «Настройки» в
поле «Оформление панели», хранится в настройках (`option theme`), поэтому
переносится вместе с остальными настройками.

Темы:

- **Классическая** — как было: меню сверху, карточки;
- **Компактная** — плотные отступы, узкие поля, кнопки в строку: удобно, когда
  функций много и хочется видеть больше на экране;
- **Тёмная** — те же раскладки, но тёмные цвета;
- **С боковым меню** — меню слева колонкой (как в PassWall), контент справа;
  на узком экране меню возвращается наверх;
- **Плитками** — крупные карточки и круглые кнопки (как в HomeProxy), удобно
  для телефона и планшета;
- **В стиле LuCI** — строгие рамки, вкладки сверху, неброские цвета, как у
  самого OpenWrt.

Как это сделано: весь каркас описан CSS-переменными, а тема лишь переопределяет
их и добавляет пару правил раскладки. Поэтому верстка не дублируется, а новые
темы добавляются одной функцией в `/usr/lib/xraypanel/themes.sh`. Заодно
тихие обновления (перекраска строк раз в 10 секунд) переведены с «жёстких»
цветов на классы, чтобы в тёмной и других темах они выглядели правильно.

## Старый реверс в новых сборках xray (0.16.2)

Проверено на живых бинарниках: в xray 25.x и новее **старый реверс удалён**.
Бинарник 26.7.28 с конфигом, где есть `reverse.bridges`, вообще отказывается
запускаться:

    Failed to start: common/errors: The feature "legacy reverse" has been
    removed and migrated to "VLESS Reverse Proxy".

Это значит: на роутере с новым xray панель со старым способом реверса не просто
«не отправит трафик» — xray не поднимется совсем, вместе с обычным туннелем.
Что сделано:

- при применении конфига панель распознаёт такую ошибку, убирает блок
  `reverse` и собирает конфиг заново — xray запускается, мосты временно
  выключены;
- на странице «Реверс» появляется предупреждение с объяснением и тем, что
  нужно сделать.

Как устроен новый способ («VLESS Reverse Proxy»), если захочется перейти:

- на сервере-портале у нужного клиента во VLESS-входе добавляется
  `"reverse": {"tag": "имя-выхода"}` — этот тег становится обычным выходящим
  тегом для маршрутизации;
- на роутере у VLESS-выхода, который смотрит на портал, добавляется
  `"reverse": {"tag": "имя-входа"}` — этот тег становится входящим для правил
  маршрутизации;
- теги на двух концах не обязаны совпадать, их связывает сама обратная
  сессия, а домен больше не нужен;
- важно: старый и новый способ нельзя смешивать — либо оба конца на 25+, либо
  оба на старом реверсе (как сейчас у нас: на сервере стоит бинарник 24.12.31
  именно для этого).

## Удобство: строки, интерфейсы, маршруты, мобильный вид (0.16.2)

- **Активные строки больше не «подсвечиваются» цветом в разметке.** Раньше
  панель писала `style="background:#ecfdf5"` прямо в строку сервера или моста,
  и в тёмной теме она оставалась светлой. Теперь это классы `row-ok`/`row-bad`,
  а цвет берётся из темы — тёмная тема остаётся тёмной.
- **Кнопка «основной»** вместо «сделать основным» — теперь она той же ширины,
  что и «изменить», и оформлена так же.
- **Интерфейсы сети снова можно выбирать**, но по-человечески: галочки в
  раскрывающемся списке, а под ним строка «Выбрано: …». По умолчанию галочка
  стоит на LAN-мосте роутера, можно отметить и второй LAN, и WAN. Если нужного
  интерфейса в списке нет — осталось поле для ручного ввода.
- **Список «кого заворачивать»** теперь включает и постоянные аренды DHCP, и
  текущие выданные адреса — то есть видны и устройства с фиксированным
  адресом, и те, что получили его от роутера.
- **«Что заходило в перехватчик»** всегда выводится в столбик: нашлась причина,
  почему строки иногда склеивались — при сборке JSON переводы строк
  вырезались. Теперь они экранируются, и записи не слипаются даже после
  тихого обновления страницы.
- **На «Маршрутах» появился блок «Куда идёт остальное»** — сразу видно, что
  будет с трафиком, который не попал ни под одно правило: уходит на выход по
  умолчанию, на балансировщик (если включён автовыбор) или напрямую.
- **Страница «Конфиг»**: на диске показывается тот конфиг, с которым xray
  работает сейчас, а «что получится по текущим настройкам» спрятано под
  раскрывающийся заголовок — дублировать его на виду больше не нужно.
- **Из «Настроек» убрана галочка автовыбора по пингу** — она дублировала выбор
  на странице «Прозрачно». Заодно исправлено: сохранение остальных настроек
  больше не выключает автовыбор, а выбор конкретного сервера в «Куда
  направлять» теперь честно выключает балансировщик (раньше он оставался
  главным, и настройка не действовала).
- **Мобильный вид.** На узком экране (до 640 px) строки таблиц серверов,
  мостов и правил превращаются в карточки: каждое поле подписано слева, а
  значение справа — длинные строки больше не расползаются по экрану.

## Вкладка «Серверы»: цвета и мобильный вид (0.16.2)

В 0.9.2 список на странице «Статус» поправили, а саму вкладку «Серверы» — нет.
Теперь и там:

- активный сервер помечается классом темы, а не жёстким светлым фоном в
  разметке — в тёмной теме строка больше не светится белым;
- таблица стала адаптивной: на узком экране строки превращаются в карточки с
  подписями (Имя / Тег / Адрес / UUID / Действия).

Проверено, что жёстких цветов в разметке панели больше не осталось вообще —
все берутся из темы.

## Проверка узлов по URL, статистика трафика (0.16.2)

**Проверка «по-настоящему», а не пингом.** Пинг показывает только доступность
адреса: узел может отвечать на пинг и не работать. Теперь панель поднимает на
секунду отдельный xray (вход на 127.0.0.1 смотрит на тестовый адрес, выход —
на проверяемый сервер), качает через него тестовую страницу и меряет время:

- на странице «Серверы» в колонке «Проверка» виден результат и время
  (`250 мс` зелёным, `нет ответа` красным);
- кнопка «проверить» у каждого узла — проверка идёт сразу, ответ видно в
  сообщении;
- кнопка «проверить все» — все узлы проверяются в фоне;
- тестовый адрес и порт проверки задаются в «Настройках» (по умолчанию
  `http://www.gstatic.com/generate_204`, порт 18999).

Проверено на живом сервере: рабочий узел — 1,4 секунды на круг вместе с
запуском xray (сам ответ ~250 мс), мёртвый узел обрывается по таймауту.
Без ограничения по времени проверка висела бы минутами — wget по умолчанию
повторяет попытки.

**Автоматическая проверка.** В «Настройках» можно включить периодическую
проверку (каждые 5/15/30/60 минут) — панель добавляет задачу в cron, а
`/usr/lib/xraypanel/urltest.sh` обновляет результаты в таблице.

**Статистика трафика.**

- по узлам: панель спрашивает счётчики у самого xray через его API
  (`xray api statsquery`) и показывает в таблице «↑ отправлено / ↓ принято»
  с момента запуска xray;
- по клиентам: для режима «только адреса из списка» панель теперь ставит по
  одному правилу на клиента, поэтому у каждого свой счётчик, и на странице
  «Прозрачно» появился блок «Трафик по клиентам» (пакеты и объём). Счётчики
  начинаются заново при каждом включении режима.

Осталось из списка: подписки (загрузка узлов по ссылке) и поддержка
Shadowsocks / Hysteria2 / WireGuard — это следующая версия.

## Протоколы и подписки (0.16.2)

**Новые протоколы выходов.** Кроме VLESS+Reality сервер может быть
Shadowsocks, Hysteria 2 или WireGuard. В форме сервера появился выбор
протокола, а поля показываются только те, что нужны выбранному:

- Shadowsocks: метод шифрования и пароль (пишем старый, вложенный формат
  настроек — его понимают и старые, и новые сборки xray: проверено на 24.12.31
  и 26.7.28);
- WireGuard: приватный ключ клиента, публичный ключ сервера, адрес клиента,
  allowedIPs, MTU;
- Hysteria 2: пароль, SNI, «не проверять сертификат» (allowInsecure).

**Hysteria 2 и старые сборки.** Транспорт hysteria появился только в xray 25+.
На 24.x конфиг с таким сервером xray вообще не запускает, поэтому панель
ловит это при проверке, убирает такие серверы из конфига и пишет в журнал:
«ваша сборка xray не умеет Hysteria 2 (нужен xray 25+) — такие серверы
временно убраны». Обычный туннель при этом продолжает работать. Проверено на
живых бинарниках 24.12.31 и 26.7.28.

**Ссылки.** Импорт по ссылке теперь понимает не только `vless://`, но и
`ss://` (оба варианта: с base64-парой и целиком закодированный) и
`hysteria2://` (`hy2://`), включая параметры `sni` и `insecure`.

**Подписки.** На странице «Серверы» появился блок «Подписки»:

- добавляете адрес подписки (и, если нужно, свой User-Agent — некоторые
  серверы отдают список только определённым клиентам, например `v2rayNG/1.8.5`);
- панель скачивает список, раскодирует base64 (или читает как есть), разбирает
  ссылки и сама создаёт серверы;
- у каждого подписочного сервера сохраняется пометка, откуда он пришёл —
  поэтому при обновлении заменяются только его узлы, а ваши личные серверы
  не трогаются;
- «обновить» — вручную, либо в «Настройках» можно включить автообновление
  (каждые 6/12/24 часа, задача добавляется в cron,
  скрипт `/usr/lib/xraypanel/sub-update.sh`).

## Исправление подписок и мобильный вид (0.16.2)

При первой же проверке подписок нашлись две вещи:

- **Раскодирование не работало.** Функция `b64d` принимала строку аргументом, а
  в конвейере аргумента нет — значит она декодировала пустоту. Из-за этого
  панель решала, что подписка «не раскодировалась», и брала файл как есть.
  Теперь `b64d` умеет и то, и другое: строку аргументом или поток со входа.
- **В сообщение попадала чужая ошибка** вида `tr: write error: Broken pipe` —
  это следствие той же неудачи: `base64` завершался, а `tr` продолжал писать.
  Все служебные ошибки раскодирования теперь подавлены.

Заодно раскодирование стало устойчивее: если подписка отдаёт base64 без
выравнивания (`=` в конце нет), панель сама дописывает его. Проверено на трёх
вариантах подписки — base64 с выравниванием, base64 без выравнивания и просто
список ссылок: во всех случаях узлы создаются.

Мобильный вид: таблица подписок (как и остальные) превращается в карточки,
длинный адрес подписки переносится по строкам, а кнопки «обновить»/«удалить»
переносятся на новую строку, если не помещаются.

## VMess и Trojan, трафик по клиентам (0.16.2)

**Подписки чаще всего состоят не из VLESS.** Поэтому добавлены ещё два
протокола: **VMess** (ссылка `vmess://` — это base64 от JSON; панель читает
адрес, порт, id, сеть tcp/ws, путь, Host, TLS и SNI) и **Trojan**
(`trojan://пароль@адрес:порт?sni=...`). Оба выхода проверены на живых xray
24.12.31 и 26.7.28 — конфиг принимается.

Сообщение об обновлении подписки теперь подробное: видно, сколько ссылок
нашлось, сколько узлов добавлено и какие схемы панель не понимает, например:
«ссылок в подписке: 7, добавлено узлов: 3, не поддерживаю схемы: vmess trojan».

Ещё одна несовместимость: в xray 26 ключ `allowInsecure` в TLS удалён (вместо
него pinnedPeerCertSha256). Панель его больше не пишет — иначе на новых
сборках конфиг не собирался бы. Для Hysteria 2 этот параметр остался (он
внутри её собственных настроек и работает).

**Трафик по клиентам.** Раньше показывался только объём «вверх» — поэтому
цифры и казались маленькими: у клиента основной трафик идёт вниз. Теперь
панель считает оба направления:

- «отправлено» — счётчик в цепочке `pre` (клиент отдаёт трафик в перехватчик);
- «принято» — отдельный счётчик в цепочке `outf` (xray возвращает ответы
  клиенту уже от имени сайтов).

Таблица обновляется сама раз в 10 секунд, без перезагрузки страницы.

## Сброс трафика без перезагрузки, клиенты в маршрутах, методы ss (0.17.0)

**Кнопка «сброс» больше не дёргает страницу.** Раньше нажатие на «сброс» у
клиента отправляло форму и страница перезагружалась целиком — прыгала прокрутка
и терялось место, где вы были. Теперь кнопка отправляет запрос тихо (fetch) и
просто обнуляет цифры в строке этого клиента. То же самое у кнопки «сбросить
трафик у всех»: все значения в таблице становятся «0 Б», страница никуда не
уезжает.

**Клиентов в «Маршрутах» теперь видно списком.** Раньше адрес клиента
приходилось вписывать руками (подсказки datalist на телефоне вообще не
показываются). Теперь рядом с полем «Значение» есть обычный выпадающий список с
именами и адресами устройств: постоянные аренды DHCP плюс те, кто сейчас
подключён. Выбрали устройство — адрес подставился в поле. В поле «Тип» при
редактировании правила вернулся вариант «source — клиент (кто идёт)»: раньше
список был только ip/domain, и при сохранении такого правила тип молча терялся.

**Shadowsocks: методы.** Поддерживаются все методы, которые знает xray 24.12.31
(проверено живым `xray run -test`):

- `aes-128-gcm`, `aes-256-gcm`, `chacha20-ietf-poly1305`, `xchacha20-ietf-poly1305`;
- `2022-blake3-aes-128-gcm`, `2022-blake3-aes-256-gcm`,
  `2022-blake3-chacha20-poly1305` (это и есть «black»).

На странице сервера метод выбирается из списка. При сохранении и при импорте
ссылки панель проверяет длину ключа для методов `2022-blake3`: 16 байт для
aes-128, 32 байта для aes-256 и chacha20 — ключ должен быть base64. Если длина
не та, панель скажет прямо (например «ключ метода 2022-blake3-chacha20-poly1305
— это base64 на 32 байта, а тут 16»), потому что с неправильным ключом xray
сервер не поднимает.

**Разбор ссылок `ss://` стал всеядным.** Панель понимает все три вида:

- `ss://base64(метод:пароль)@адрес:порт` — обычный (SIP002);
- `ss://метод:пароль@адрес:порт` — открытым текстом (так отдают sing-box и часть
  подписок). Именно такие ссылки раньше ломались: панель пыталась разобрать
  открытый текст как base64 и получала мусорный метод — сервер добавлялся, но не
  работал;
- `ss://base64(метод:пароль@адрес:порт)` — самый старый вид с `#именем`.
  Здесь нашлась ошибка: пароль брался от последнего двоеточия, то есть вместо
  пароля в него попадал порт.

Проценты в ссылке (`%2B`, `%2F`, `%3D`) теперь раскодируются до разбора, а
хвостовой «/» перед параметрами больше не портит порт. Если в ссылке есть
`plugin=` (SIP003), панель помечает такой сервер в списке как «нужен плагин» —
xray такие плагины не умеет, и узел без него не заработает.

## Маршруты по-новому: устройство + куда идём, порядок правил, тихие проверки (0.17.0)

**Правило теперь собирается из трёх понятных пунктов.** Раньше нужно было
придумать имя, выбрать тип (ip/domain/source) и только потом вписать значение —
и легко было ошибиться. Теперь в форме всего три поля:

1. **Устройство (кто идёт)** — список ваших устройств с именами из DHCP; пусто
   значит «все». Адрес можно и вписать руками (например целую сеть
   `192.168.11.0/24`).
2. **Куда идём** — адрес, сеть или домен (`8.8.8.8`, `10.0.0.0/8`,
   `youtube.com`, `geosite:openai`). Тип панель определяет сама — выбирать
   «ip или domain» больше не нужно.
3. **Через что выходим** — сервер, `direct`, `blocked`, маршрут через
   интерфейс, а также новый вариант **«по пингу»** (самый быстрый сервер —
   балансировщик xray).

Заполнять нужно не всё: только устройство — «этот клиент идёт как решено
ниже»; только «куда идём» — правило для всех; и то и другое — «этот клиент на
этот адрес» (в конфиге получается одно правило с двумя условиями `source` и
`ip`/`domain`). В списке правил теперь видно устройство — именем и адресом, а
не только цифрами.

**Порядок правил.** xray смотрит правила сверху вниз и останавливается на
первом подходящем. Поэтому «частное» правило должно стоять выше общего,
например «клиент → youtube.com напрямую» надо поставить выше «этот клиент →
через сервер». В таблице правил появились кнопки **↑** и **↓** — они меняют
порядок (он хранится отдельным номером и учитывается и в конфиге xray, и в
маршрутах через интерфейс).

**«Подтвердить конфиг» на странице «Маршруты»** больше не перебрасывает на
«Статус» — вы остаётесь там, где были.

**Проверка сервера** кнопкой «проверить» на странице «Серверы» идёт тихо: без
перезагрузки и прыжков страницы. Кнопка на время проверки показывает
«проверяю…», а в колонке «Проверка» сразу появляется новое время отклика (или
«нет ответа»).

**Мелочь по ходу дела:** выход «по пингу» в правилах включает балансировщик
`auto` вместе с наблюдателем (observatory) — без наблюдателя xray отказывался
стартовать, поэтому теперь панель добавляет его сама, даже если автовыбор не
включён как основной режим.

**Правила маршрутизации важнее выбранного сервера.** Нашлась неприятная
ошибка: если на странице «Прокси» в поле «Куда направлять» выбран конкретный
сервер, панель писала правило «весь перехваченный трафик → этот сервер» и
ставила его в начало списка правил. А xray останавливается на первом подходящем
правиле — значит, все ваши правила маршрутизации просто не срабатывали
(«маршруты работали, только если выбрано „по правилам панели“»). Теперь это
правило-«всё остальное» идёт **последним**: сначала проверяются ваши правила,
и только то, что под них не попало, уходит на выбранный сервер. Поле на
странице «Прокси» переименовано в «Куда направлять правила не решили», чтобы
смысл был виден сразу.

## Маршруты «через интерфейс» и DNS: что мешало правилам (0.18.0)

**Правило «через интерфейс …» вообще не работало при включённом прокси.**
Такие правила панель выполняет не в xray, а в ядре Linux: ставит `ip rule`
и свою таблицу маршрутов. Но пакет клиента сначала попадал в перехватчик
(`redirect` в nft) — адрес назначения подменялся на адрес роутера, пакет уходил
в xray, и до маршрутизации ядра дело не доходило. Теперь перехватчик отпускает
такие потоки раньше, чем заворачивает остальное (`return` в нужной цепочке), и
ядро отправляет их в выбранный интерфейс. Одновременно маршруты через интерфейс
пересчитываются при включении прокси, а не только по кнопке «Применить конфиг»,
и для интерфейса теперь берётся его шлюз (`via`), а не только `dev` — с одним
`dev` маршрут через WAN-интерфейс работает не на всех сборках.

**Про домены и DNS.** xray в этом режиме «подсматривает» имя сайта из TLS
(SNI) и HTTP-заголовка Host — поэтому правила по домену работают даже когда
DNS идёт мимо туннеля, а правило по адресу сравнивается с настоящим адресом
сайта, который выбрал клиент.

## Счётчики трафика по клиентам не считали (0.18.1)

Трафик клиента считали правила-счётчики в той же цепочке, что и перехватчик,
но стояли они **после** правила `redirect`. А после `redirect` цепочка дальше
не идёт — то есть счётчики не видели ни одного пакета. Отсюда и «трафик
клиента не считается», и «у клиента из маршрута трафика не видно вовсе».

Теперь счётчики живут в отдельных цепочках и ничего не решают (политика
accept, вердиктов нет):

- `ctr` (hook prerouting, приоритет -150) — «отправлено» клиентом: считается
  весь интернет-трафик, включая тот, что уходит мимо прокси по правилу «через
  интерфейс»;
- `ctrd` (hook forward) — «принято» для трафика, который идёт транзитом (не
  через прокси);
- `outf` (hook output) — «принято» для прокси: ответы клиенту отдаёт сам xray.

Панель складывает все три. Сброс счётчика у клиента переставляет только
правила-счётчики (в этих цепочках порядок не важен), сброс у всех — обнуляет
все счётчики. Учтите: трафик, который уходит мимо прокси (правило «через
интерфейс»), в журнале xray не появится — он там и не проходит, он виден
только в счётчике трафика.

## Правило можно выключить, не удаляя (0.18.2)

Рядом с «изменить» и «удалить» появилась кнопка **«выключить»**. Выключенное
правило остаётся в списке (серым, с пометкой «выключено»), но уходит из
конфига xray — как будто его нет. Кнопка превращается в «включить» и
возвращает правило обратно. После нажатия, как обычно, нужно нажать
«Подтвердить конфиг».

Зачем: чтобы проверять правила по одному, не пересоздавая их каждый раз — и
не забыть, что это правило было. Выключенное правило не попадает ни в конфиг
xray, ни в маршруты через интерфейс (ядровые `ip rule`), ни в «отпускание»
трафика мимо перехватчика в nft. Удобно и для проверки «а точно ли дело в этом
правиле».

## Применение конфига без перезагрузки страницы (0.61.0)

Раньше «Применить конфиг» / «Подтвердить конфиг» работали как обычная отправка
формы: браузер уходил на страницу заново, и это выглядело как перезагрузка.
Теперь кнопка отправляет запрос тихо:

- над кнопкой появляется «Конфиг применяется…», сама кнопка становится
  «Применяется…» и гаснет;
- как только xray перезапустился, надпись меняется на «Конфиг применён, xray
  перезапущен», а пометка «Изменено, но ещё не применено» и кнопка в шапке
  пропадают;
- если xray не поднялся и панель вернула прежний конфиг — об этом так и
  написано, с последней строкой журнала применения;
- на странице «Конфиг» блок «Различия с файлом на роутере» сразу заменяется на
  «файл на роутере совпадает с настройками»;
- страница при этом никуда не перезагружается: остаётся там же, где вы были.

Как это работает внутри: панель запускает применение в фоне, кладёт рядом
файлы-пометки (`apply.running` — идёт, `apply.rc` — итог), а страница раз в
полторы секунды спрашивает состояние (`?page=jobs`) и переписывает надписи.

## Правила по доменам — как в PassWall: списки адресов (0.62.0)

**Отклонено: код этой версии убран, сборка лежит в `old-versions/`.**

Проблема была такая: правило по домену работает, но в журнале xray вместо имени
сайта стоит адрес (`accepted tcp:142.251.98.132:443 [transparent -> direct]`),
и панель не может понять, какое правило поймало трафик. Лампочка у правил по
доменам не горела, и казалось, что они не работают.

Теперь панель делает то же, что PassWall: заводит **свой набор адресов на
каждое правило по домену** и просит dnsmasq складывать туда адреса разобранных
имён. Дальше панель сверяет адрес из журнала с наборами и точно знает, какое
правило сработало.

- наборы — `nft`-таблицы `inet xraypanel_dom`, по набору `xp_<раздел>_4` на
  правило (адреса IPv4);
- строки для dnsmasq лежат в `<каталог настроек dnsmasq>/xraypanel-rules.conf`
  (по умолчанию `/tmp/dnsmasq.d`, каталог берётся из настроек dnsmasq);
- панель пишет файл только если сборка dnsmasq умеет `nftset`. Если не умеет —
  файл не пишется вовсе (иначе dnsmasq не поднимется и на роутере пропадёт
  DNS), а в панели появляется пояснение;
- после записи панель перечитывает настройки dnsmasq и проверяет, что он жив:
  если не поднялся — файл убирается, dnsmasq поднимается снова;
- наборы живут в памяти, поэтому собираются заново при загрузке роутера, при
  каждом применении конфига и при открытии страницы «Маршруты», если их нет;
- имена берутся из правил: `domain:` и `full:` — как написано, `geosite:` —
  разбором файла со списками (до 2000 имён на правило). `keyword:` и `regexp:`
  в наборы не попадают: dnsmasq понимает только «домен и все поддомены».

Что это даёт на практике: лампочка у правила по домену загорается, когда
трафик по нему действительно идёт; в подсказке к лампочке видно, когда это было
и сколько адресов поймано; в блоке «Что именно уходит в xray» у каждого правила
написано число адресов в его наборе, а под таблицей правил — общий итог.

Ограничение то же, что у PassWall: если имя разбирает не роутер (например,
браузер с шифрованным DNS), адрес в набор не попадёт и правило по домену в
панели не подсветится. На саму маршрутизацию это не влияет: xray по-прежнему
разбирает имена сам (sniffing), поэтому правила по доменам работают и без
наборов.

## Тихие кнопки по всей панели и ускорение «Маршрутов» (0.63.0)

**Отклонено: код этой версии убран, сборка лежит в `old-versions/`.**

В 0.61–0.62 «тихими» стали только применение конфига и стрелки правил, а все
остальные кнопки (сохранить сервер, выключить правило, удалить мост и так

  ответа сервера, перезагрузки нет;
- переходы по меню панели тоже без перезагрузки;

- «живое» обновление (раз в 10 секунд) включается и после тихого перехода на
  другую страницу панели.

## Лампочки: точные и «по выходу» (0.64.0)

**Отклонено: код этой версии убран, сборка лежит в `old-versions/`.**

Панель узнаёт попадание правила двумя разными способами — поэтому лампочки у
правил выглядят по-разному, и это не ошибка:

- **точно** — правила по адресу (`ip`) и по домену (`domain:`, `full:`): панель
  сверяет адрес из журнала xray со списком адресов этого правила (наборы
  dnsmasq + nft). Лампочка залита цветом: зелёная — только что, жёлтая — в
  последние минуты;
- **«по выходу»** — правила по шаблону (`regexp:`, `keyword:`) и готовые списки
  (`geosite:`, `geoip:`): в журнале стоит адрес, а в правиле — слово или
  шаблон, поэтому панель видит только то, что трафик ушёл через выход этого
  правила. Такая лампочка обведена, а не залита, и в подсказке написано
  «проверено по выходу». Это может быть и совпадение: например, правило
  `regexp:youtube -> direct` подсветится от любого трафика, ушедшего напрямую.

Что изменилось по существу: точное попадание теперь всегда важнее «по выходу».
Раньше правило по шаблону могло «забрать» лампочку у доменного, если стояло
выше него в списке; теперь доменное подсвечивается, даже если шаблонное стоит
выше.

И ещё: если у правила по домену адреса ещё не собраны, в подсказке прямо
написано почему — имена разбирает не роутер (в браузере может быть включён
шифрованный DNS) либо изменения ещё не применены кнопкой «Применить конфиг».
Наборы адресов собираются в момент применения конфига.

## Скорость «Прокси» и «Маршрутов» и порядок сбора списков (0.65.0)

**Отклонено: код этой версии убран, сборка лежит в `old-versions/`.**

Эти две страницы грузились по 15–25 секунд. Причины нашлись две:

1. **Сбор списков адресов мог зацикливаться.** Наборы для правил делались после
   разбора готовых списков, а разбор большого списка (`geosite:CATEGORY-RU`)
   на роутере идёт долго. Получалось так: панель снова и снова запускала сбор,
   каждый раз упиралась в тяжёлый разбор, из-за чего не успевали появиться
   вообще все наборы — вместе с наборами для простых правил `domain:`/`full:`.
   Теперь:
   - сначала делаются наборы для простых правил (`domain:`, `full:`) — это
     мгновенно, и лампочки по ним начинают работать;
   - готовые списки (`geosite:`) разбираются отдельно и позже, результат
     разбора кэшируется на неделю, а сам разбор ограничен по времени;
   - второй сбор не запускается, пока идёт первый (замок), а со страницы
     «Маршруты» сбор просится не чаще раза в 5 минут.
2. **Журнал xray читался целиком.** Живое обновление и страница «Прокси»
   искали строки по всему файлу журнала (а он растёт), причём каждые 10 секунд.
   Теперь читается только хвост журнала.
3. **Статистика трафика спрашивалась по несколько раз за показ страницы.**
   Каждый запрос — это отдельный запуск бинарника `xray` (`api statsquery`).
   Теперь ответ держится в кэше 10 секунд.

Заодно на странице «Маршруты» появилась кнопка **«проверить списки адресов»**:
она показывает, что именно мешает (нет `nft`, dnsmasq без `nftset`, не тот
каталог настроек, пустые наборы), и строку «Последняя сборка списков».

## Несколько правил на одно имя — наборы в одной строке (0.66.0)

**Отклонено: код этой версии убран, сборка лежит в `old-versions/`.**

Проверка на роутере показала: у правил `domain:youtube.com` и
`full:youtube.com` адреса были только у одного набора, у второго — ноль. Причина
в dnsmasq: если для одного имени задано несколько строк `nftset=`, адрес
попадает только в один набор (берётся первое подходящее правило dnsmasq).
Поэтому теперь наборы для одного имени перечисляются в **одной строке**:

    nftset=/youtube.com/4#inet#xraypanel_dom#xp_r5_4,4#inet#xraypanel_dom#xp_r6_4

Так адрес получают сразу все правила, которым это имя нужно (и `domain:`, и
`full:`, и `geosite:` с тем же доменом), и лампочки загораются у всех.

Ещё раз про то, какие правила панель может проверять точно:

| тип правила | как проверяется |
|---|---|
| `ip` | точно — по адресу |
| `domain:` / `full:` | точно — по списку адресов правила (dnsmasq + nft) |
| `geosite:` | точно по списку адресов (для тех имён, что разбирались через роутер), иначе «по выходу» |
| `geoip:` | «по выходу» (обведённая лампочка) |
| `keyword:` / `regexp:` | «по выходу» (обведённая лампочка) |

  Теперь ответ держится 10 секунд в файле, и запусков `xray` стало в разы

## 0.61.2 — «сбросить трафик у всех» действительно обнуляет

Кнопка «сбросить трафик у всех» не сбрасывала: числа на странице оставались
прежними. Одиночные кнопки при этом работали.

Причина: кнопка «у всех» делала одну команду `nft reset rules chain` на всю
цепочку со счётчиками и её ошибку глушила. На роутере эта команда счётчики не
обнуляла — то есть сбрасывать было нечего, а выглядело это как «трафик
вернулся». Одиночная кнопка устроена иначе: находит правило-счётчик клиента и
переставляет его заново, поэтому счётчик честно начинается с нуля.

Что сделано:

- «сбросить у всех» сначала по-прежнему пробует быстрый штатный сброс, но
  теперь **проверяет результат** — сколько байт было в счётчиках до и после;
- если быстрый способ не сработал, панель проходит по всем клиентам со
  счётчиками и переставляет их правила — тем же способом, что и одиночные
  кнопки (он рабочий);
- в сообщении панель пишет, каким способом обнулила и сколько клиентов
  затронуто, а если что-то осталось — предупреждает об остатке.

Файлы: `usr/lib/xraypanel/lib.sh` (`client_counters`, `client_counters_sum`,
`client_counter_ips`, новый `traffic_reset`), `www/cgi-bin/xraypanel`
(сообщение о результате).

## 0.61.3 — лампочки по именам сайтов (по журналу запросов dnsmasq)

До этого правила по домену, слову и шаблону панель проверить не могла: в журнале
xray вместо имени сайта стоит адрес (`accepted tcp:142.250.1.1:443`). Поэтому
точными были только правила по адресу, а всё остальное отмечалось «по выходу»
(у `regexp:`), либо не горело вовсе (у `domain:`, `full:`, `keyword:`).

Теперь на странице «Маршруты» есть переключатель **«проверить по именам
сайтов»**:

- панель просит dnsmasq записывать разобранные имена в отдельный файл
  (`/tmp/xraypanel-dns.log`), включая запись запросов; прежние значения
  `logqueries` и `logfacility` сохраняются, и выключение возвращает их назад;
- из строк вида `reply www.youtube.com is 142.250.1.1` панель строит карту
  «адрес → имя» (читается только хвост файла, файл подрезается, чтобы не рос);
- дальше для каждой записи журнала xray по адресу находится имя сайта и с
  правилом сверяется **имя**: `domain:` — домен и поддомены, `full:` — ровно
  этот домен, `keyword:` — слово в имени, `regexp:` — шаблон по имени;
- в подсказке к лампочке (`title`) и в списке «за 10 минут» видно уже имена
  сайтов, а не адреса: например `www.youtube.com (3), rr1---sn-….googlevideo.com (2)`.

Как и у PassWall, видны только те имена, которые клиенты разбирают через
роутер. Если в браузере включён свой «защищённый DNS» (DoH/DoT), имени в журнале
не будет — тогда правило снова проверяется как раньше («по выходу»), а чтобы
имена были видны, надо либо выключить шифрованный DNS в браузере, либо включить
перехват DNS на странице «Прокси».

Файлы: `usr/lib/xraypanel/lib.sh` (`dns_log_*`, изменения в `rules_activity`),
`www/cgi-bin/xraypanel` (действия `dnslog_on`/`dnslog_off` и блок на
«Маршрутах»).

## 0.61.4 — имена сайтов без отдельного файла (исправление 0.61.3)

В 0.61.3 панель просила dnsmasq писать запросы в **отдельный файл**
(`logfacility=/tmp/xraypanel-dns.log`) и сама подрезала этот файл. На роутере
это привело к потере связи: у клиентов пропадал интернет, помогало только
выключение настройки и перезагрузка роутера. Извиняюсь — эту версию ставить
не стоит.

Что сделано в 0.61.4:

- **отдельного файла больше нет.** Панель добавляет dnsmasq только одну
  штатную настройку — `logqueries=1` (запись запросов), а имена читает из
  обычного системного журнала (`logread`). Никаких файлов панель не создаёт,
  не подрезает и не трогает;
- прежнее значение `logqueries` запоминается и возвращается при выключении;
- **перед включением** панель проверяет, что dnsmasq вообще работает: если он
  не запущен, настройки не меняются вовсе;
- **после включения** панель проверяет, что dnsmasq не упал. Если упал —
  настройка сразу возвращается как была, dnsmasq запускается заново, а панель
  пишет об этом прямо («вернул прежние настройки»);
- при выключении, если dnsmasq почему-то не работает, панель не «перечитывает
  настройки», а запускает службу заново — раньше именно этого не хватало,
  чтобы связь вернулась без перезагрузки роутера;
- если на роутере остались следы 0.61.3 (`logfacility=/tmp/xraypanel-dns.log`),
  панель их убирает и при включении, и при выключении.

Всё остальное из 0.61.3 (проверка правил по имени сайта, показ имён в
подсказках) работает как описано выше — изменился только способ получения
имён.

## 0.61.5 — запись запросов включается перезапуском dnsmasq и проверяется

Проверено на живом роутере: 0.61.4 включала запись запросов, настройка в файле
появлялась (`log-queries=extra`), но dnsmasq, которому послали «перечитать
настройки», её не применял — и панель показывала «включено», а имён было 0.
Плюс отдельная причина, которую нашли в ходе проверки: в `/etc/dnsmasq.conf`
может стоять `log-facility=/dev/null` — тогда dnsmasq вообще ничего не пишет в
журнал, сколько бы настроек мы ни включали.

Что сделано:

- включение и выключение записи запросов теперь идёт через **перезапуск**
  dnsmasq (не «перечитать настройки») — только так настройка применяется;
- после включения панель **проверяет результат**: сама делает один запрос имени
  через роутер и смотрит, появились ли строки-ответы в системном журнале;
- если записи не появились, панель прямо говорит, что мешает, и находит ту
  самую строку `log-facility=/dev/null`, объясняя, что её надо закомментировать
  и перезапустить dnsmasq;
- на странице «Маршруты» при включённой проверке и нуле имён показывается это
  предупреждение, а не молчаливое «включено»;
- при выключении, если dnsmasq не работает, панель его запускает (а не просто
  «перечитывает настройки»).

Проверено на испытательном роутере: после правки `/etc/dnsmasq.conf` (строка
`log-facility=/dev/null` закомментирована, копия файла сохранена рядом как
`dnsmasq.conf.bak-…`) и перезапуска dnsmasq панель увидела имена — у правила
`domain:youtube.com` в подсказке появилось `www.youtube.com`, у соседнего
правила `rr3.sn-3c27sn7l.googlevideo.com` и `google.com`.

## 0.61.6 — имена обновляются и при «живом» обновлении страниц

Карта «адрес → имя» пересобиралась только тогда, когда открывали страницу
«Маршруты» (именно она её заказывала). Поэтому на других страницах имена могли
быть устаревшими — до следующего захода на «Маршруты».

Теперь карта обновляется и при «живом» обновлении, которое идёт раз в 10 секунд

Проверено на испытательном роутере: после установки 0.61.6 имена обновляются
сами (достаточно было открыть «Статус», без захода на «Маршруты»).

## 0.61.7 — имена помнятся дольше, чем живёт журнал

Системный журнал на роутере короткий: 64 КБ, и при включённой записи запросов
он покрывает всего 4–5 минут. Панель строила карту «адрес → имя» только из
этого окна, поэтому старые соединения (например, разобранные 20 минут назад)
оставались без имени — и правило по домену могло не подсветиться.

Теперь панель ведёт свою историю имён в `/etc/xraypanel/dns-names.hist`:

- свежие записи из журнала перекрывают старые;
- имя помнится час (`XRAYPANEL_DNS_KEEP`, по умолчанию 3600 секунд);
- всего не больше 2000 записей (`XRAYPANEL_DNS_MAX`), самые старые
  отбрасываются — файл не растёт;
- карта для проверки правил (`dns-names.map`) собирается уже из этой истории;
- при выключении записи запросов история стирается вместе с картой.

Дополнительно на испытательном роутере увеличен системный журнал: с 64 КБ до
256 КБ (`uci set system.@system[0].log_size=256`), чтобы и в панели, и в LuCI
(«Статус» → «Системный журнал») было видно вчетверо больше запросов.

## 0.61.10 — VLESS через WebSocket (серверы за CDN)

Проверка на роутере показала: сервер, который на телефоне работает по
WebSocket, панель собирала как обычный VLESS + Reality (TCP) — и даже с пустым
публичным ключом, из-за чего xray отказывался запускаться целиком
(`Failed to build REALITY config: empty "publicKey"`). Поля «Сеть», «Путь» и
«Host» в форме сервера были доступны только для vmess, а для vless панель
всегда писала `network: tcp`.

Что сделано:

- в форме сервера поля **«Сеть (tcp или ws)», «Путь», «Host»** теперь
  показываются и для VLESS, с пояснением: `tcp` — обычный Reality (нужен pbk),
  `ws` — WebSocket через CDN (тогда заполняются «Путь» и «Host», а Flow
  оставляется пустым — с ws он несовместим);
- генератор конфига для VLESS с `network=ws` пишет правильный транспорт:

      "streamSettings":{"network":"ws","security":"tls",
        "tlsSettings":{"serverName":"<sni>"},
        "wsSettings":{"path":"<путь>","headers":{"Host":"<host>"}}}

  без Reality и без flow (проверено на стенде: JSON корректный; при пустом sni
  получается `security: none`, при `tcp` — прежний Reality, как и было);
- при сохранении сервера панель предупреждает, если выбран VLESS+Reality без
  публичного ключа: «без него xray не запустится; если это WebSocket — укажите
  Сеть: ws»;
- импорт ссылок понимает `type=ws`, `path`, `host`, `security=tls` — такой
  сервер можно добавить, просто вставив ссылку с телефона.

## 0.61.11 — исправление: проверка сервера уходила не туда

Проверка сервера («проверить» и подбор по пингу) собирала временный конфиг, где
в правилах маршрутизации указывался тег вида `srv-tls` — то есть сервер,
которого нет. xray писал в журнал `non existing outTag: srv-tls`, соединение
шло «наугад» и проверка всегда заканчивалась «нет ответа».

Причина: в ветке генератора для WebSocket (0.61.10) я использовал имя
переменной `_sec` — а оно занято вызывающим кодом, там лежит имя (раздел)
сервера. Значение затиралось словом `tls` из настроек TLS, и в правило
попадало `srv-tls`.

Исправлено: в ветке WebSocket все переменные свои (`_wsnet`, `_wsec`, `_wtls`,
`_wpath`, `_whost`), имя сервера больше не затирается. Проверено на живом
роутере отдельным тестом: до правки — «нет ответа», после правки — 204.

## 0.61.12 — починена статистика трафика (служебный вход API)

Панель не могла показать байты по серверам: обращение к API xray всегда
заканчивалось `failed to dial 127.0.0.1:62789`, а на странице «Прокси» висело
«Статистика xray пока пустая».

Разобрался на живом роутере: порт слушается, `nc` к нему подключается, а
клиент API — нет. Собрал два одинаковых временных конфига и сравнил: с
настройкой `"settings": {"address": "127.0.0.1"}` API отвечает, а с той, что
писала панель — `"settings": {"rewriteAddress": "127.0.0.1"}` — клиент API
получает «failed to dial». То есть служебный вход был описан неверно, и это
ломало всю статистику по выходам (она и в 0.60 не работала — та же ошибка была
в самом первом сообщении).

Исправлено: служебный вход API теперь пишется как в официальном примере —
`"settings": {"address": "127.0.0.1"}`. Отдельно проверил, что в конфиге есть
`"stats": {}` и `policy` со счётчиками — они на месте.

Что это даёт: на «Прокси» в блоке «Куда идёт трафик» появятся байты по каждому
выходу, а в таблице серверов — столбик с общим трафиком (если включить).

## 0.61.13 — счётчики выходов без настройки policy

Байты по серверам всё равно не считались, хотя API уже отвечал. Причина: в
конфиге не было блока `policy` с `statsInboundUplink` / `statsOutboundUplink` —
без него xray считает только трафик по пользователям, а по выходам нет.
Добавлено: панель сама пишет этот блок в конфиг.

## 0.61.14 — счётчики клиентов, кнопка «сделать основным», галочки клиентов

Три вещи, которые просил пользователь.

1. **Трафик по клиентам в режиме «вся локальная сеть».** Раньше счётчики
   ставились только на адреса из DHCP-аренд: статика и новые устройства не
   попадали. Теперь и «вверх», и «вниз» считаются наборами nft со счётчиками
   (`cli4`, `cli4dn`) — адрес попадает в набор сам, как только с него пошёл
   трафик, поэтому считаются все, включая статику. Сброс трафика («у всех» и у
   одного клиента) чистит эти наборы — счётчики начинаются с нуля.

   Отдельная причина, почему трафик пропал в 0.61.2–0.61.13: в скрипт
   перехвата `transparent.sh` подключается `lib.sh`, и одноимённая функция
   `client_counters` из библиотеки перекрывала ту, что создаёт счётчики.
   Функции библиотеки переименованы в `panel_counters_dump`,
   `panel_counters_sum`, `panel_counter_ips`.

2. **Кнопка «сделать основным» на странице «Серверы».** Ставит выбранный
   сервер выходом по умолчанию (весь трафик без своего правила идёт через
   него). У текущего основного сервера вместо кнопки — пометка «основной».
   Заодно эта кнопка выключает «автовыбор по пингу»: иначе автовыбор главнее,
   и настройка не действовала бы.

3. **Галочки клиентов.** По умолчанию отмечены все. Пустой список панель
   читает как «все, включая тех, кто появится позже» — ошибки в режиме «вся
   локальная сеть» больше нет. Рядом с таблицей кнопки «отметить всех» и
   «снять все» и короткая подсказка, как читается пустой список.

## 0.61.15 — смена версии из панели, понятные ошибки, живой трафик

Семь правок по просьбам пользователя.

1. **Выбор клиентов только там, где он нужен.** Кнопки «отметить всех» и
   «снять все» убраны. В режиме «вся локальная сеть» блока выбора клиентов нет
   вообще (заворачиваются все — и DHCP, и статика, и новые устройства), как и в
   режиме «только сам роутер». Галочки остались только для режима «только
   клиенты из списка». Таблица трафика по клиентам остаётся видна всегда.
2. **Смена версии панели из панели.** На странице «Статус» появился блок
   «Смена версии панели»: список найденных пакетов `.ipk` (по умолчанию `/tmp`
   и `/etc/xraypanel/versions`) с кнопкой «поставить», загрузка своего файла с
   компьютера и кнопка «вернуть прежнюю версию». Настройки, серверы и правила
   не трогаются. Файл читается побайтно, поэтому пакет не портится; перед
   установкой панель запоминает, что стояло до неё.
3. **Понятная причина, почему не поднялся перехват.** Панель сама находит в
   журнале ту строку, из-за которой всё сломалось, и объясняет её человеческим
   языком: занятый порт, неизвестный выход у правила или моста, непрочитанный
   конфиг, нехватка прав, сброшенные счётчики xray и так далее. Плюс — что
   сделать и сама строка журнала (полный хвост остался под спойлером).
4. **«Проверка» и «Что именно заворачивается»** убраны под спойлеры — страница
   стала короче.
5. **«только адреса из списка» → «только клиенты из списка»**.
6. **«Куда идёт трафик» обновляется живьём**: байты и доли пересчитываются раз
   в 10 секунд без перезагрузки страницы. История теперь суммируется со
   свежими байтами xray, поэтому числа растут, а не «замирают» до следующего
   снимка.
7. **Строка «Трафик» в «Прозрачном режиме»** тоже обновляется живьём — как у
   клиентов в таблице.

Одна лампочка в «Маршрутах» горела постоянно. Разобрался по журналу xray: из
200 последних записей настоящими были меньше половины, остальное — служебная

## 0.61.17 — проверка сервера объясняет причину отказа

Кнопка «проверить» у сервера умела сказать только «нет ответа» — и было
непонятно, что именно случилось: сервер закрыл соединение, не тот путь,
не проходит TLS, нет маршрута. Особенно мешало это на серверах через CDN
(Cloudflare и подобные), где ошибка возникает уже после открытия WebSocket.

Теперь проверочный xray запускается с уровнем журнала `info`, его вывод
пишется в `/etc/xraypanel/last-test.log`, и панель объясняет причину словами:

- «сервер закрыл соединение, клиента не признал» — типичный случай, когда на
  сервере нет такого UUID или он отключён;
- «сервер не нашёл путь (404)» — путь или Host не совпали с настройками входа;
- «не удалось открыть WebSocket», «сертификат сервера не принят»,
  «сервер отклонил соединение — порт закрыт», «нет маршрута до сервера»,
  «сервер не ответил вовремя», «соединение оборвалось без ответа».

Причина показывается и в столбце «Проверка» (короткой подписью), и строкой под
таблицей серверов, а полный журнал последней проверки доступен там же под
спойлером «журнал последней проверки (подробно)».

Дополнительно проверка переведена на **HTTP-прокси-вход** вместо dokodemo-door.
С dokodemo клиент (wget) обращался к 127.0.0.1, и в запросе уходил заголовок
`Host: 127.0.0.1`; серверы, которые проверяют Host или блокируют приватные
адреса, наглухо отбрасывали такой запрос — проверка показывала «нет ответа»
при полностью рабочем сервере (именно так и было с сервером через Cloudflare).
С HTTP-прокси-входом заголовок Host подставляется правильно.

Ещё одна деталь: проверочный адрес из настроек должен быть доступен **через
сам сервер**. Если через конкретный выход не открывается `www.gstatic.com`,
проверка будет «нет ответа» — тогда смените адрес (например на

## 0.66.9 — два способа реверса, выбор у каждого моста

Раньше панель умела только старый реверс (порталы и мосты по домену). В новых
сборках xray его убрали (начиная с 26.4.25) и заменили на «VLESS Reverse Proxy»
по тегу. Теперь панель умеет оба, и способ выбирается **у каждого моста
отдельно** (или берётся общий, как у роутера).

Как это выглядит:

- в форме моста появилось поле **«Способ реверса»**: «как у роутера», «старый —
  по домену», «новый — VLESS Reverse Proxy по тегу»;
- в списке мостов появился столбец **«Способ»**: видно, какой мост как собран;
- домен теперь нужен только старому способу — для нового поле можно оставить
  пустым (панель больше не требует домен у нового моста).

Что происходит с конфигом:

- мосты со старым способом собираются в блок `reverse.bridges` (как раньше);
- мосты с новым способом попадают в свой выход как
  `"reverse": {"tag": "имя-моста"}` — причём панель пишет упрощённый вид выхода
  (`address/port/id` прямо в `settings`), потому что в обычном виде с `vnext`
  xray эту пометку молча игнорирует и туннель не поднимается;
- трафик из туннеля приходит с тегом моста, поэтому правила маршрутизации для
  мостов работают без изменений — и у старого, и у нового способа.

Проверено на xray 26.4.17: конфиг с новым реверсом принимается
(`Configuration OK`), старый реверс на этой же версии тоже работает. Важно:
чтобы мост с новым способом заработал, **на сервере-портале** нужен xray 25.9.11
или новее — там трафик для моста направляется на тот же тег.

Ещё в этой же сессии на роутере заменён сам xray: было 24.12.31 из репозитория
OpenWrt, стало **26.4.17** (официальный статический бинарник; прежний сохранён
как `/usr/bin/xray.bak-24.12.31`). Причина: 26.4.17 — самая свежая версия,
которая понимает **оба** способа реверса. Все три моста после замены
подключились, панель работает.

## 0.66.11–0.66.12 — точные миллисекунды, понятная причина отказа, однострочные таблицы

Собрано после того, как выяснилось: у сервера `revers` порт открыт и пинг идёт,
а проверка из панели всегда отвечает «нет ответа».

Что показала диагностика (только чтение, панель тогда не менялась):

- вход `revers` (free.johnglab.online:45763) принимает клиента, но сразу
  закрывает соединение — на любой адрес, даже на 1.1.1.1, и даже с заведомо
  неправильным клиентом. Значит, это вход под реверс (он же служит выходом для
  моста `germ_revers`), а не выход в интернет. Проверка панели скачивает через
  сервер тестовую страницу, поэтому у такого входа она пройти не может — это не
  поломка панели;
- цифры проверки были фикцией: запрос уходил в фон, а панель ждала результат
  циклами по 1 секунде. На роутере нет ни `timeout`, ни дробного `sleep`, поэтому
  у всех серверов выходили одинаковые «круглые» 1000 / 1010 / 1020 мс.

Что сделано:

- **точный замер проверки**: время берутся из часов ядра (`/proc/timer_list`,
  наносекунды) прямо вокруг запроса, три попытки, берём лучшую. Значения стали
  настоящими — например 512.1 мс, 446.8 мс, 291.1 мс. Если файла часов в системе
  нет — панель откатывается на `/proc/uptime`;
- **понятная причина отказа**: если узел принял клиента и сразу закрыл
  соединение, панель пишет, что это либо портал реверса (когда сервер занят
  мостом), либо не совпали данные клиента — uuid/flow на входе или ключ Reality
  (pbk, shortId, SNI);
- **страница «Реверс»**: новая колонка «Отклик» — живой замер (пинг) выходного
  сервера моста в реальных миллисекундах; тексты состояния укорочены (адрес и
  порт и так видны в столбце «Выход»), поэтому строка больше не разъезжается;
- **вёрстка в одну строку** на страницах «Реверс» и «Серверы»: длинные значения
  (имена, теги, адреса, состояние) обрезаются с «…», а полный текст показывается
  подсказкой при наведении мышки. На телефоне это же работает в карточках.

Версия 0.66.12 — правка подсказки о причине: она различает случай «сервер занят
мостом» (`revers` → «это портал реверса») и «не совпали ключи» (`Germ_Vless-WRT`
→ «проверьте uuid/flow/Reality»).

Попутно видно по проверке: `Germ_Vless-WRT` (44333) и `VLESS-CDN-WS-haus` (443)
сейчас действительно не работают — REALITY-вход и WebSocket-вход закрывают
соединение, не признавая клиента. Это уже на стороне сервера, не панели.

ограничение xray, а не панели.


## 0.66.14 — после сохранения моста панель возвращает к списку

возвращала.

Причина: сохранение идёт «тихим» способом (без перезагрузки страницы), и в
ответе сервера не было поля с тем, куда вернуться. Страница получала только
текст сообщения и оставалась там же, где была.

Что сделано:

- сервер теперь вместе с сообщением говорит, на какую страницу вернуться;
  страницы-редакторы (мост, сервер, правило) после сохранения уходят на свой
  список, а страницы-списки по-прежнему обновляются на месте;
- сообщение («реверс-мост сохранён…») передаётся при переходе, поэтому видно
  его уже на странице «Реверс»;
- то же самое касается удаления моста или сервера прямо из формы
  редактирования — раньше после удаления форма оставалась на экране.

В форме моста был только выбор «direct / blocked / сервер», то есть трафик из

## 0.66.17 — смысл пунктов «домашняя сеть» и «direct» поменяли местами

Пользователь попросил иначе: «домашняя сеть» должна пускать и в домашнюю сеть,
и в интернет, а `direct` — **только** в интернет, чтобы домашнюю сеть можно было
закрыть.

Что сделано:

- `lan` («домашняя сеть и интернет») → отдельный выход `rev-home` с разрешением
  всего (`0.0.0.0/0`, `::/0`) — и домашняя сеть, и интернет через домашний канал;
- `direct` («только интернет») → отдельный выход `rev-net`, у которого первым
  правилом идёт запрет домашних и служебных диапазонов (`10/8`, `172.16/12`,
  `192.168/16`, `127/8`, `169.254/16`, `100.64/10`, `fc00::/7`, `fe80::/10`),
  а следом разрешение всего остального. Правила проверяются по порядку, поэтому
  домашняя сеть закрыта, а интернет работает;
- значение по умолчанию для нового моста — «домашняя сеть и интернет»;
- `blocked` и «через сервер» остались как были.

Проверено на роутере (версия 0.66.17): у моста `germ_revers` стоит «домашняя
сеть и интернет», в конфиге правило
`{"inboundTag":["wrt-tag"],"outboundTag":"rev-home"}`, ссылки на `rev-net` нет
(её добавляет только режим «только интернет»). С сервера через туннель роутер
доступен: 3 запроса из 3 вернули страницу, SSH по туннелю заходит.

## Важно про flow у реверс-моста (разбор 24.09.2026)

Симптом: «реверс вроде поднят, но никуда не попасть — ни в домашнюю сеть, ни
через другой сервер». TCP-соединение с порталом висело, ошибок в журнале xray не
было, но в туннель не приходило ни одного запроса.

Причина: **рассогласование `flow`**. У нашего выхода моста стояло
`flow: xtls-rprx-vision`, а на сервере у этого же клиента flow пустой. В таком
виде сервер не признаёт соединение как реверс-туннель: связь устанавливается, но
обратный туннель не регистрируется, поэтому трафик в него не идёт вообще — и
любой выбранный в панели выход остаётся бесполезным.

Лечение на первом шаге: у нашего выхода flow убрали
(`uci delete xraypanel.<раздел>.flow`), конфиг применили. Сразу после этого
пошли запросы, и в журнале роутера видно уже не только сам роутер, но и домашнюю
сеть:

```
accepted tcp:192.168.99.95:80 [wrt-tag -> rev-home]
accepted tcp:192.168.99.1:80  [wrt-tag -> rev-home]     # Keenetic
accepted tcp:192.168.99.95:22 [wrt-tag -> rev-home]     # SSH
```

Проверено с сервера через туннель: `http://192.168.99.95/` и
`http://192.168.99.1/` отдают 200 (второй — «KeeneticOS Web Panel»), SSH по
туннелю заходит.

Дальше пользователь на сервере выставил у клиента `flow: xtls-rprx-vision` — и
мы вернули flow и у себя (`uci set xraypanel.<раздел>.flow=xtls-rprx-vision`).
Проверка после этого: с сервера через туннель открываются и роутер (200), и
Keenetic (200, «KeeneticOS Web Panel»), SSH по туннелю заходит. Значит работает
и так.

Вывод на будущее: **flow у клиента на сервере и у нашего выхода моста должны
совпадать.** Работает и «у обоих пусто», и «у обоих `xtls-rprx-vision`»; ломается,
когда значения разные — тогда сервер не регистрирует реверс и туннель молчит.
Сейчас у нас выставлено `xtls-rprx-vision` (как и на сервере).

## 0.66.25 — панель проверяет шаблон (regexp) перед сохранением

Пользователь заметил: в поле «Шаблон» панель принимает вообще всё, что впишешь.
Проверка показала, что это опасно — xray собирает регулярные выражения при
загрузке конфига, и с битым шаблоном **вообще не запускается**:

```
Failed to start: main: failed to create server > error parsing regexp: missing closing ): `(`
```

Что сделано: добавлена функция `regexp_ok()` — шаблон «примеряется» к строке тем
же движком регулярных выражений, и запись не сохраняется, если выражение не
разбирается (пустое, незакрытая скобка, битый escape). Проверка стоит в трёх
местах: добавление записи в набор, сохранение изменённых записей набора и
сохранение правила. Сначала проверяем, потом пишем в настройки — при ошибке
панель пишет «шаблон с ошибкой — не сохраняю: …» и ничего не меняет.

Проверено на роутере: значение `(` не сохранилось (панель ответила сообщением об
ошибке), а `(^|\.)(vkvideo|rutube)\.ru$` сохранилось и попало в конфиг правильно
экранированным:

```
"domain": ["domain:vkvideo.ru", …, "regexp:(^|\\.)(vkvideo|rutube)\\.ru$"]
```

Попутно в наборе пользователя нашлась запись с лишним слэшем перед `|`
(`(^|\.)(vkvideo\|rutube)\.ru$`) — такой шаблон синтаксически верен, но ищет
домен с литеральным символом `|`, то есть не ловит ничего. Запись исправлена;
стоит помнить, что проверка ловит только «сломанные» шаблоны, а «не тот по
смыслу» лучше проверять кнопкой «Проверка домена».


## 0.66.26 — конструктор шаблона и проверка при вводе

Просьба: не получать упавший xray из-за забытой точки или скобки, а собирать
шаблон из сайтов, при ошибке — подсвечивать красным и не сохранять.

Что сделано:

- **проверка при вводе**: если в поле «Значение» (или при правке записи в

## 0.66.27 — панель больше не отдаётся из кэша браузера

## 0.66.28 — шаблон, который «ловит всё», тоже не сохраняется

Пользователь заметил: `(((` и битый слэш панель подсвечивает, а `kino|.`
проходит как ни в чём не бывало. Формально это правильное выражение, но по сути
оно ловит **любой** домен (`.` — любой символ), и правило с ним заворачивает
весь трафик. Такое теперь тоже не сохраняется.

Что добавлено в проверку (и в браузере, и на сервере):

- шаблон не разбирается → красное поле, «шаблон не разбирается — проверьте
  скобки, квадратные скобки и экранирование точки»;
- лишний слэш перед `|` → «это лишний слэш: для „или“ пишите просто |»;
- шаблон совпадает со строкой без букв и точек (как `kino|.` или `.*`) →
  «шаблон совпадает со всем подряд — правило поймает все домены; для всего
  трафика есть отдельный пункт в „Куда“»;
- точка перед доменной зоной не экранирована (`.ru` вместо `\.ru`) —
  предупреждение.

Что по-прежнему разрешено (это настоящие шаблоны): `rutube`, `.*\.ru$`,
`\.ru$`, `(^|\.)(vkvideo|rutube)\.ru$`.

Проверено в движке JavaScript (jsdom) на живой странице: `kino|.`, `(((`, `.*` —
красное поле, сообщение и запрет сохранения; `rutube` и собранный шаблон —
проходят нормально. Та же логика проверена и на стороне сервера.

## 0.66.34 — обе кнопки «применить конфиг» показывают одно и то же

## 0.66.37 — активность правил и записей считается «как у xray»

Пользователь: «правила срабатывают в одном наборе, а лампочка мигает в другом».
Разбор на живом роутере выявил две причины.

**1. Записи набора подсвечивались по чужому трафику.** `set_items_activity`
брала просто свежие адреса из журнала и подсвечивала все записи набора, которые

**2. Порядок правил не учитывался.** Xray берёт первое подходящее правило сверху
вниз, а панель разбирала «неточные» правила (готовые списки geosite/geoip) во
вторую очередь — и активность могла попасть на строку, через которую трафик в

vkvideo/rutube/ya.ru, набор «шаблон» (правило выше) — только ozon/psbank.


## 0.66.38 — лампочки горят одинаково и гаснут за 30 секунд, звук кнопок

Пользователь: «при срабатывании правила лампочка что в правиле, что в наборе
загорается максимально ярко и постепенно при отсутствии импульса бледнеет в
течение 30 секунд; если ловит срабатывание — тут же опять максимальная яркость
и затухание 30 секунд. Звук кнопок попробуем».

Что сделано:

- Одно окно на всю панель: `LAMP_SECONDS=30`. Строка правила и запись набора
  вспыхивают ярко и гаснут за 30 секунд; новое срабатывание — снова максимум.
  Раньше пороги были разные (правило — 300 с, запись набора — 10/60 с), из-за
  этого казалось, что лампочки «живут своей жизнью».
- Затухание рисует сам браузер (CSS-анимация `lampfade`, 30 с), поэтому оно
  плавное, хотя состояние панель спрашивает раз в 4 секунды. Позицию внутри
  окна задаёт `animation-delay:-<возраст>s` — лампочка стоит на месте и после
  перезагрузки страницы, и на другом устройстве.
- Правило и запись набора берут данные из одного ответа роутера в одном такте,
  поэтому горят и гаснут синхронно.
- Найден и исправлен настоящий баг: правило **без источника** не получало
  лампочку никогда. `rules_activity` разбирала строку `rule_conditions` через
  `read`, а пустое поле «съедалось» — остальные поля сдвигались влево, и правило
  («весь трафик») оставалось без активности. Теперь поля режутся `cut` — пустые
  сохраняются.
- Звук кнопок: синтезируется браузером, файлов в пакете нет. Выбор в
  «Настройках» — выключен / щелчок (по умолчанию) / тик / блип / два тона
  (вверх — обычные кнопки, вниз — удаление), плюс громкость (тихо/средне/громко).
- Отклик кнопки: короткая вспышка (`box-shadow`) и вибрация на Android — видно,
  что нажатие дошло, даже когда сохранение идёт тихо, без перезагрузки страницы.
- Нюанс, который обойти нельзя: браузеры разрешают звук только после первого
  касания страницы, поэтому до первого нажатия панель молчит.

Проверено на локальном стенде: строка правила и запись набора получают
`class="lamp-on" style="animation-delay:-Ns"` при свежем срабатывании и гаснут
после 30 секунд; звуковые настройки сохраняются и видны на всех страницах.


## 0.66.39 — лампочки в наборах с готовыми списками стали точными

Пользователь: «кнопки заработали, правила вроде бы срабатывают. Но в правиле
telegram лампочка работает, а в наборе ни одна запись не светится, хотя должно».

Что оказалось. Правило панель проверяет по журналу xray: видит адрес, куда ушёл
трафик, и решает, какое правило его поймало. Запись набора вида «готовый список»

`/etc/xraypanel/geosite.<ИМЯ>.domains`, а его на роутере почти не было (только

- новый скрипт `geo-item.sh`: разбирает списки, которые реально стоят записями в

- панель на «Маршрутах» сама запускает этот разбор, когда видит неразобранный
  список, и пишет об этом прямым текстом («Готовые списки набора ещё не
  разобраны: TELEGRAM …»). Есть и кнопка «разобрать списки набора» рядом с
  управлением наборами;
- в подсказке у записи теперь сказано, почему она показана «вероятно» и что
  нужно нажать;
- активность правил проверяется по разобранному списку доменов, а не «по
  выходу»: правило с `geosite` больше не приписывает себе чужой трафик. Раньше

  домены (проверка идёт по имени сайта из журнала запросов dnsmasq; если имя
  неизвестно, поведение прежнее — «по выходу»);
- «вероятно» больше не пишется про списки, которые уже разобраны: либо точное
  совпадение, либо ничего.

Проверено на локальном стенде: домен из списка (`video.vk.com`) — запись набора
и правило горят синхронно; домен не из списка — ни правило, ни запись не
подсвечиваются (чужой трафик не приписывается).


## 0.66.40 — информативный блок «Готовые списки» и автообновление баз

Пользователь: «Обновление баз не информативное — непонятно, разобраны базы или
нет, и как часто их нужно разбирать: одного раза достаточно или после каждого
обновления? Раньше было информативнее, там было поле, откуда скачивается.
Может, сделать автоматический режим».

Разбор: подробный блок с файлами и источниками в коде был, но со страницы
«Маршруты» его убрали (остались только две кнопки) — отсюда и ощущение, что
стало хуже. Ответ на «как часто разбирать»: названия и списки наборов
разбираются один раз, а заново — только после обновления файлов баз; панель
делает это сама.

Что сделано:

- карточка «Готовые списки» теперь в пять понятных частей:
  1) таблица файлов баз: путь, что внутри (домены/адреса), размер, дата
     изменения и сколько названий дал именно этот файл (0 — красным «не
     разобрался»);
  2) таблица «Списки из наборов»: имя, доменов, когда разобран, состояние
     «актуален / надо разобрать заново / не разобран» + кнопка разбора;
  3) обновление из интернета: выбор источника и **настоящие адреса загрузки**
     (Loyalsoldier, v2fly, runetfreedom) прямо под ним;
  4) сводка последнего обновления: дата, источник и что именно поставлено —
     её пишет `geo-update.sh` в `geo-update.last` (раньше это было видно только
     в журнале);
  5) три журнала под спойлерами (обновление, сбор названий, разбор списков
     наборов);
- автообновление баз: «выключено / раз в неделю (понедельник, 4 утра) / раз в
  месяц (1-е число, 4 утра)» + источник для автообновления; задание ставится в
  cron (`cron_set_geo`), в карточке видно текущее состояние. По умолчанию
  выключено;
- `geo-update.sh` после удачного обновления сам пересобирает названия и разбор
  списков наборов (раньше приходилось нажимать вручную), а сводку пишет только
  при успехе — «последнее обновление» не покажет то, чего не было;
- ответы для «тихих» кнопок блока теперь в формате панели (`geo_ajax_reply`), а
  сама карточка (`#geo-card`) перерисовывается на месте, без перезагрузки.
- заодно убрана лишняя работа роутера: `file_size()` берёт размер файла через
  `ls`, а не `wc -c < файл` (busybox при этом читает geosite.dat целиком — 10–17

## 0.66.42 — лампочки больше не показывают не то правило

Пользователь: «лампочки мигают как угодно, не на тех правилах».

Причина оказалась не в лампочках, а в источнике имён сайтов. Панель понимает,
какое правило поймало трафик, по именам из журнала запросов dnsmasq:
`rules_activity` сопоставляет адрес из журнала xray с именем сайта, и уже по
имени проверяет условия правил (готовые списки, домены, шаблоны). На роутере
25.09 в 15:43 упал системный журнал:

```
kern.info kernel: logd[1315]: segfault at 7f31f0fbf902
```

После этого dnsmasq перестал писать в журнал (проверено: `logread | grep -c
dnsmasq` → 0, а `log-queries=extra` в его конфиге есть). Имена панель держит час,
поэтому до ~16:45 старые ещё работали, а потом кончились — и условия правил
стало нечем проверять. Правило `r1` (набор «Прокси» с `geoip:ru`) стоит первым,
поэтому оно забирало себе весь трафик: панель показывала, что по `r1` прошёл
`173.194.153.197` (Google) с выходом `LLHost-Vless-Wrt`, то есть на самом деле
сработало `r2` (набор youtube).

Что сделано:

- **двухпроходный подсчёт**. Раньше панель шла строго по порядку правил и
  первое же «подходящее по выходу» забирало трафик. Теперь сначала ищется
  ТОЧНОЕ совпадение (условие проверено: разобранный готовый список, известное
  имя сайта, точный адрес/домен), и только если точного нет — второй проход «по
  выходу», как раньше. Функция `val_ok` заменена на `val_kind` (0 — не подходит,
  1 — точно, 2 — по выходу);
- **видно, когда лампочки могут врать**. Появилась `dns_names_state` (ok / off /
  nolog / silent) и предупреждение на «Маршрутах»: если запись запросов
  выключена — кнопка «включить запись запросов DNS», если dnsmasq потерял
  системный журнал — кнопка «починить сейчас» и объяснение, почему лампочки
  могут показывать не то правило;
- **автопочинка**: в состоянии «dnsmasq молчит» панель сама перезапускает
  dnsmasq, но не чаще раза в час (`dns_try_repair`). Раньше кнопка «починить» в
  панели была только в коде — на страницу её не вывели, поэтому починить было
  нечем.

Проверено на локальном стенде: при известном имени сайта трафик уходит на
правило с разобранным списком (хотя правило с `geoip` стоит выше), а без имён —
второй проход отдаёт его первому правилу, как и раньше.


## 0.66.43 — списки адресов (geoip) проверяются по адресу

Продолжение 0.66.42. После починки журнала dnsmasq имена сайтов вернулись, но
часть соединений идёт к адресам, чьих имён роутер вообще не видел: по журналу
видно, что клиент значительную часть имён разбирает не через роутер (свой
шифрованный DNS), плюс много ответов приходит по IPv6. По карте «адрес →
правило» было 5 записей по имени и 18 по адресу. Для таких соединений условие
`geoip:ru` (правило `r1`, оно первое) проверить было нечем, и оно забирало себе
весь трафик.

Что сделано:

- **разборщик `geo-ip-list.awk`** — вытаскивает диапазоны адресов готового
  списка из `geoip.dat`. Файл этот — protobuf, и байт 0x0A в нём встречается и
  как разделитель строк, поэтому обычное чтение «по строкам» разрезает сами
  диапазоны (`0x12 0x08 0x0A 0x04 <адрес> 0x10 <маска>`). Разборщик собирает
  поток обратно: склеивает куски, возвращая разделитель, и переносит хвост
  между кусками, чтобы шаблон нашёлся на границе. Для `ru` получается 12 992
  диапазона;
- `geo-item.sh` теперь разбирает не только домены, но и адреса:
  `geoip.<ИМЯ>.cidr`. Списки берутся из условий правил (`rule_conditions`), то
  есть и из наборов, и из старых правил с полями;
- в `rules_activity` добавлены `geoipload` (складывает диапазоны в таблицу
  «сдвиг:начало сети») и `geoip_check` (проверка адреса — 33 обращения вместо
  перебора тысяч диапазонов). У `val_kind` для geoip теперь три состояния:
  1 — адрес в списке, 0 — нет, 2 — проверить нечем (нет разобранного файла или
  в журнале не IPv4);
- **второй проход стал умнее**: если точного совпадения нет, панель сначала
  примеряет правила с конкретным выходом, который совпал с выходом из журнала
  (у таких правил видно, через какой именно сервер ушёл трафик), и только
  третьим проходом берёт первое попавшееся правило, как раньше;
- в блоке «Готовые списки» таблица показывает и домены, и адреса (что внутри,
  сколько записей, когда разобран), а записи наборов типа `geoip` тоже
  подсвечиваются по точному совпадению адреса.

Проверено на локальном стенде: адрес из списка (`2.16.20.5` при списке `ru`) —
правило с `geoip:ru` определяется точно, даже если имя сайта неизвестно; адрес
не из списка — это правило больше его не забирает, и трафик уходит на правило,
чей выход совпал с выходом из журнала (раньше его забирало первое правило сверху).

### Подписки и Hysteria: что нашлось дальше

Пользователь: «WireGuard даже не добавляется по подписке; Hysteria добавилась, но
проверку не проходит — по-моему Hysteria на xray не работает».

**WireGuard из подписки.** Обновление подписки (`sub_update`) принимало только
`vless://`, `ss://`, `hysteria2://` и `hy2://` — ссылки `vmess://`, `trojan://` и
`wireguard://` молча считались «неподдерживаемыми» и пропускались. Из-за этого
WireGuard-сервер из подписки не появлялся в панели, хотя разбор такой ссылки в
`server_add_from_link` был. Теперь принимаются и они (включая `wg://`), а из
ссылки читается ещё и `allowedips`.

Проверено живьём: WireGuard-сервер из подписки разбирается (приватный ключ,
публичный ключ, адрес 10.0.0.3/32, MTU), собранный выход проходит `xray run
-test`, и через него реально проходит запрос (две попытки `wget` через
HTTP-прокси — код 0). Напомню, что для работы в панели в WG-выход добавлен
`"noKernelTun": true` — без него xray падал на `CreateTUN("wg0")`.

**Hysteria.** Панель собирала выход так:
`{"protocol":"hysteria",...,"streamSettings":{"network":"hysteria","hysteriaSettings":{...}}}`
— без блока TLS. Xray на это отвечал
`transport/internet/hysteria: tls config is nil`, и проверка сервера всегда
заканчивалась «нет ответа». Теперь в конфиг пишутся `"security":"tls"` и
`tlsSettings` (имя для проверки сертификата — из SNI, а если его нет, из адреса
сервера; `allowInsecure` — если в ссылке было `insecure=1`), а поле SNI в форме
сервера показывается и для Hysteria.

**Но конкретный сервер из подписки всё равно не заработает.** В ссылке есть
маскировка:

```
hysteria2://…@free.johnglab.online:443?alpn=h3&fp=chrome&obfs=salamander&obfs-password=…&security=tls&sni=…
```

`obfs=salamander` — это маскировка Hysteria 2 (sing-box). В xray её нет: строка
`salamander` в бинарнике относится к другому механизму (`transport/internet/
finalmask/salamander`, новая маскировка транспортов Xray), полей вида
`obfsPassword` в xray вообще нет (проверено `grep` по бинарнику). Поэтому клиент
xray отправляет обычный Hysteria 2-хендшейк, сервер с obfs его отбрасывает —
в журнале видно `timeout: no recent network activity` (это уже после исправления
TLS; до него ошибка была про `tls config is nil`).

Вывод для пользователя: сервер с obfs нужно либо освободить от obfs (тогда он
заработает и в xray, и в панели), либо оставить для sing-box. Hysteria 2 без obfs
панель теперь собирает корректно.

### Кнопка проверки обновления: почему её было не видно

Пользователь: «должна быть и кнопка для проверки обновления».

Кнопка была, но карточка «Обновление панели» по ошибке печаталась в
`page_header()` — то есть попадала в `<head>` (строка 6 HTML) и лезла на все
страницы сразу, а на «Статусе» выглядела как случайная плашка. Плюс результат
проверки не появлялся сам: страница не перерисовывала эту карточку.

Что сделано:

- карточка вынесена в отдельную функцию `update_card_html()` и печатается только
  на странице «Статус» (в нормальном месте — после блока «Состояние»), у неё
  появился `id="update-card"`;
- добавлена отдельная лёгкая страница `?page=update_card` — она отдаёт только
  эту карточку;
- пока идёт проверка (в карточке видно «Проверяю новые версии…»), страница сама
  опрашивает `?page=update_card` каждые 2,5 секунды (до 20 раз) и подменяет
  карточку — результат (новая версия, «что нового», ошибка) появляется без
  перезагрузки;
- сама кнопка теперь называется «проверить обновление сейчас» и работает тихо:
  после нажатия карточка сразу показывает «Проверяю…», а потом результат;
- карточка добавлена в список «живых» блоков, которые панель перерисовывает
  после тихих действий.

Проверено на роутере: карточка только на «Статусе» (в `<head>` её больше нет),
кнопка на месте, `?page=update_card` отдаёт карточку, все страницы открываются
без ошибок.

### «Идёт через wg», а панель показывала «напрямую» и rev-home

Пользователь: «выход по правилу маршрутизации идёт через wg, так и есть, но в
клиенте показывает напрямую, а в статистике выше и вовсе rev-home».

Проверил журнал xray — пользователь прав: соединения идут
`[transparent -> wg]`. Ошибки были в самой панели, две:

1. **«Сейчас в работе» показывало rev-home.** `active_server_now()` брала все
   строки журнала, включая трафик обратного моста (`[wrt-tag -> rev-home]`) —
   это выпуск того, что портал гонит в домашнюю сеть, а не сервер, к которому
   подключается роутер. Так как такого трафика много, в «сейчас в работе»
   оказывался `rev-home`. Теперь служебные выходы мостов (`rev-*`) исключены.

2. **В таблице клиентов («Прозрачный режим» → «идёт через») показывался самый
   частый выход за две минуты.** Клиент за окно успевает сходить и напрямую, и
   через правило, и часто побеждал `direct` — в колонке появлялось «напрямую»,
   хотя последний его трафик ушёл, например, в `wg`. Теперь сначала берётся
   последний выход, который НЕ «напрямую» и не «заблокировано» (то есть выход
   правила), а остальные выходы этого клиента показываются рядом с их
   свежестью: `wg · 7 сек назад · 77.52.212.205 (ещё: напрямую (23 с))`.

Проверено на роутере: активный выход — `wg`, у клиента 192.168.121.111 в
таблице `wg (7 сек назад)`, рядом «ещё: напрямую (23 с)».

### Hysteria «вообще не шла» и проверка обоих выходов на большом файле

Пользователь: «через wg видео идёт с обрывами, а через хистерию вообще не идёт,
хотя проверки проходят оба».

Что нашлось по Hysteria: правило `r2` отправляло трафик на выход `histeria-WRT`,
а **самого выхода в конфиге не было**, поэтому xray писал в журнал
`app/dispatcher: non existing outTag: histeria-WRT` и соединения просто
пропадали. Причина — «метка навсегда»: 18.09.2026 панель один раз не смогла
собрать конфиг с Hysteria (тогда на роутере был старый xray) и записала файл
`/etc/xraypanel/hysteria.unsupported`; с тех пор `server_available()` выкидывала
Hysteria-серверы из конфига и **никогда не снимала эту метку**, хотя панель
давно обновлена.

Что сделано:

- вместо метки — честная проверка самой сборки: `xray_hysteria_ok()` даёт
  бинарнику крошечный конфиг с Hysteria-выходом и смотрит, примет ли он его;
  ответ кэшируется рядом с версией и размером бинарника (как у проверки реверса).
  Метка на роутере удалена;
- правило, которое ссылается на выход, отсутствующий в конфиге (недоступный этой
  сборке сервер), больше не пишется — иначе трафик молча пропадал, как это и
  было с Hysteria.

После правки выход `histeria-WRT` появился в конфиге, ошибок
`non existing outTag` больше нет, и по счётчикам видно живой трафик: за 20 секунд
через Hysteria прошло около 14 КБ вверх и 1,8 МБ вниз (то есть видео пошло).

Проверка обоих выходов на большом файле (по 10 МБ, через временные конфиги
панели, чистый тест без клиентов):

| Выход | 10 МБ |
|---|---|
| WireGuard, MTU 1420 | 5,0 с |
| WireGuard, MTU 1280 | 6,2 с |
| Hysteria 2 | 3,3 с |

То есть оба выхода большие файлы тянут (Hysteria — быстрее всех). Обрывы видео
через WG, о которых говорил пользователь, в этом тесте не воспроизвелись: скорее
всего дело в качестве конкретного UDP-маршрута до сервера или в MTU — на роутере
есть поле MTU у сервера, и при обрывах стоит попробовать 1280; для видео
предпочтительнее Hysteria (QUIC сам разбирается с потерями).


## 0.67.1 — обфускация Hysteria 2 (salamander)

Пользователь: «проверь, Hysteria2 xray точно не поддерживает саламандру?»

Проверил по исходникам Xray-core: **поддерживает**, но не через поле «obfs», а как
«финальную маску транспорта» — `streamSettings.finalmask.udp` с типом
`salamander` и паролем:

```json
"streamSettings": {
  "network": "hysteria",
  "security": "tls",
  "hysteriaSettings": {"version": 2, "auth": "…"},
  "finalmask": {"udp": [{"type": "salamander", "settings": {"password": "…"}}]}
}
```

Алгоритм совпадает с Hysteria 2 (sing-box): 8 байт соли в начале пакета и XOR
полезной нагрузки с blake2b-256(ключ‖соль) — смотрел
`transport/internet/finalmask/salamander/salamander.go`. Раньше я решил, что
поддержки нет, потому что в бинарнике нет полей вида `obfsPassword`; на деле
механизм называется иначе.

Проверил живьём на сервере пользователя: с маской соединение не проходит, без
маски — проходит. Значит, конкретно его сервер обфускацию не требует (в ссылке
она указана, но сервер принимает и без неё). Тем не менее поддержку добавили —
для серверов, где обфускация обязательна.

Что сделано:

- разбор ссылок: из `hysteria2://…?obfs=salamander&obfs-password=…` панель
  сохраняет `hy_obfs=salamander` и `hy_obfs_pass`;
- форма сервера: у Hysteria появились поля «Обфускация» (нет / salamander) и
  «Пароль обфускации»;
- генерация конфига: если обфускация включена и пароль задан, в
  `streamSettings` выхода дописывается `finalmask.udp` с маской `salamander`;
  если обфускации нет — конфиг остаётся прежним (ничего лишнего не пишется);
- проверено на стенде: выход с обфускацией собирается правильно, ссылка
  разбирается, конфиг с `finalmask` проходит `xray run -test`.


## 0.67.2 — DNS-трафик клиентов и понятная подсказка про UDP

Пользователь: «udp трафик не считает?»

Разобрался и проверил на роутере:

- в таблицу «трафик по клиентам» попадает **только TCP** — счётчики живут в nft,
  а в перехватчике для каждого клиента стоит `meta l4proto tcp redirect`, то есть
  в туннель заворачивается только TCP;
- UDP/443 (QUIC) панель **намеренно блокирует**, иначе браузер уходил бы на HTTP/3
  мимо прокси;
- DNS клиентов (порт 53, UDP и TCP) идёт отдельной цепочкой `dns` в панельный
  резолвер, и там байты считаются — но в таблицу клиентов не попадали;
- xray при этом считает всё, что через него прошло, включая UDP: в его статистике
  видно вход `dns-tunnel` (у пользователя 2,7 КБ вверх / 8,4 КБ вниз), а таблица
  «Куда идёт трафик» берёт байты именно из xray — поэтому трафик через Hysteria
  (она сама поверх QUIC/UDP) в этой таблице виден.

Что добавлено:

- `client_dns_traffic()` — читает цепочку `dns` и отдаёт «адрес<TAB>байт» по
  клиентам. В таблице клиентов рядом с трафиком появилась приписка
  `DNS 3,8 КБ` (только при ненулевых значениях), с подсказкой при наведении, что
  это именно запросы клиента: ответы в эту цепочку уже не попадают, потому что
  перехват идёт в prerouting;
- в живом обновлении страницы (JSON состояния) DNS-значение тоже обновляется;
- под таблицей клиентов появилось объяснение прямым текстом: считается только
  TCP — тот трафик, который заворачивается в туннель; UDP/443 блокируется, чтобы
  трафик не уходил мимо прокси; DNS показывается отдельно.


## 0.67.3 — убрано ложное «конфиг изменён» (Broken pipe в тексте конфига)

Пользователь: «на странице маршрутов при нажатии на кнопку постоянно требует
подтвердить конфиг, а в различиях с файлом пишет: `в настройках, но в файле: head:
standard output: Broken pipe`».

Причина: в двух местах генератора конфига вывод ограничивался через `head`:

```
_dnsres=$(dns_resolver_list | head -1)
… | tr -s ',;' '  ' | tr -s ' ' '\n' | awk 'NF { print }' | head -n 4
```

Когда `head` закрывал трубу раньше, его сообщение `head: standard output: Broken
pipe` попадало в **текст собранного конфига** (панель собирала его как
`gen_config 2>&1`). Настоящий файл на роутере такой строки, конечно, не содержал,
поэтому панель каждый раз видела «расхождение» и просила применить конфиг.

Что сделано:

- в `dns_resolver_list` вывод теперь ограничивает сам `awk` (`if (++n >= 4)
  exit`) — без `head` и без оборванной трубы;
- первый резолвер берётся через `sed -n 1p` (sed читает поток до конца, `Broken
  pipe` не возникает);
- страница «Конфиг» больше не подмешивает stderr в текст конфига: если генератор
  не смог собрать конфиг, показывается отдельная плашка «Конфиг не собирается» с
  причиной, а не «расхождение»;
- в `config_text_matches` и `config_diff_lines` добавлен фильтр: строки вида
  `head: …`, `sed: …`, `awk: …` и подобные (сообщения самих утилит) в сравнении
  не участвуют — они в принципе не могут быть строками JSON-конфига.

Проверено: конфиг на роутере и сгенерированный текст совпадают, ложных
«различий» больше нет.

В тот же день — **поддержка обеих линий пакетного менеджера**. Пользователь
заметил, что `opkg update && opkg install` работает только до определённой
версии. Проверено по официальным сборкам: до 24.10 это `opkg` и файлы `.ipk`,
а с **25.12** — уже `apk` и файлы `.apk` (у 25.12.5 в пакетах `*.apk`,
у 24.10.0 — `*.ipk`).

Что сделано (этапы 1 и 2, сборку `.apk` решили делать отдельно):

- в `lib.sh` появилась прослойка, которая сама определяет менеджер:
  `pkg_mgr` (apk/opkg/none), `pkg_ext` (расширение пакетов системы),
  `pkg_update`, `pkg_add`, `pkg_del`, `pkg_add_file` (установка файла `.ipk`
  или `.apk` с проверкой соответствия системе) и `pkg_cmd` (текст команды для
  подсказок);
- все прежние прямые вызовы `opkg` заменены на эту прослойку: установка
  `xray-core`, готовых списков `v2ray-geoip`/`v2ray-geosite`, установка пакета
  панели из панели, самообновление из релиза (`update-install.sh`), ожидание
  блокировки пакетного менеджера (`install-xray.sh`), подсказки про `curl`,
  часовые пояса и ручную установку xray;
- `update-check.sh` теперь ищет в релизе файл того формата, который подходит
  системе: `.ipk` для opkg, `.apk` для apk (раньше всегда `.ipk`);
- список «поставить другую версию» и загрузка пакета файлом принимают оба
  формата (`.ipk` и `.apk`);
- в README добавлен раздел про два формата пакетов с командами для обеих линий.

Этап 3 (сделан в тот же день по просьбе пользователя): **сборка `.apk`**.
Пакеты apk v3 — это не tar.gz, а контейнер `ADB`, поэтому собираем настоящим
apk-tools 3: скрипт `build-apk.sh` берёт данные из `build/data` и вызывает
`apk mkpkg` (нужен статический `apk.static`; если его нет — качает
`apk-tools-static` из Alpine, он статический и работает в любом Linux).
Метаданные: `name: xraypanel`, `version` из `control/control`, `arch: noarch`,
`license: MIT`, `depends: uhttpd`, скрипты `post-install`/`pre-deinstall` — те же
файлы, что и в ipk. Проверено установкой в тестовый корень apk-tools 3: файлы
ложатся, права (755 у скриптов) сохраняются, метаданные читаются (`adbdump`).

Владельцы файлов в apk берутся из файловой системы сборки, поэтому релизный
`.apk` собран на самом роутере (от root): в метаданных стоит `user: root`,
`group: root`, как у пакетов OpenWrt. Если собирать `build-apk.sh` обычным
пользователем, скрипт предупредит, что владельцем запишется имя сборщика.

В релиз теперь кладутся **четыре файла**: `xraypanel_<версия>_all.ipk` и
`xraypanel_all.ipk` (для opkg) плюс `xraypanel_<версия>_all.apk` и
`xraypanel_all.apk` (для apk). В README вместо инструкций по версиям — **одна
универсальная команда**: она определяет менеджер системы (`apk` или `opkg`),
скачивает из `releases/latest` файл нужного формата и ставит его; рядом осталась
таблица «какая система — какой файл — какая команда» и вариант по шагам.

### Найдена и исправлена поломка браузерной части на OpenWrt 25.12

Пользователь: «пинги не появляются в столбике на роутере 134». Причина оказалась
серьёзнее: на странице была **ошибка JavaScript** (`Unexpected identifier
'muted'`) — падала вся браузерная часть, поэтому не работали ни пинги, ни
лампочки, ни проверки узлов.

Причина: словарь строк для браузера (`xp_js_dict` в lib.sh) собирался через
`awk`, а в **busybox-awk на OpenWrt 25.12** `gsub` с обратным слэшем в замене
работает иначе, чем в GNU awk: кавычки внутри строк не экранировались
(`class="muted"` ломало объект). На 23.05 и на сервере тот же код работал —
отсюда «на одном роутере работает, на другом нет».

Исправление: в `xp_js_dict` экранирование теперь делается вручную, символ за
символом (`\` и `"`), без `gsub` — проверено на 25.12: словарь разбирается как
валидный JSON (129 записей), в браузере ошибок нет, кнопка «замерить пинг»
заполняет столбец (проверено настоящим Chrome: 30–40 мс по всем серверам).

Сборка установлена на оба роутера (134 — apk, 95 — opkg).

### Ещё две поломки на OpenWrt 25.12: зависшие тестовые xray и короткое ожидание

Пользователь: «после копирования бэкапа с 95 на 134 всё одинаково, но два сервера
не проходят проверку». Разобрались:

- панель запускает для проверки отдельный экземпляр xray и в конце убирает его
  через `pkill`, но **в OpenWrt 25.12 `pkill` отсутствует** — проверочные
  процессы копились (на 134 нашлось 4 зависших, три держали порт 18999) и новые
  проверки не могли подняться вовсе. Теперь уборка идёт по `/proc` (без `pkill`);
- панель ждала готовности тестового xray ровно 1 секунду. На виртуальном роутере
  этого мало — проверка ложно показывала «нет ответа». Теперь панель ждёт, пока
  вход реально начнёт слушать порт (до 15 секунд).

Результат на 134: было 4 непрошедших проверки и 4 зависших процесса, стало
9 из 11 проходящих и ноль зависших. Оставшиеся два сервера (`LLHost-Vless-Wrt`,
`Baza-wrt_baza`) имеют **полностью одинаковые поля** на обоих роутерах, на 95
проходят стабильно (3 из 3), на 134 — нет (3 из 3), и в другое время суток они
отваливались и на 95: это нестабильность их сервера-портала
(`johnglab700.freemyip.com` = 45.158.81.51), а не панели.

### Откат правок (по просьбе пользователя, 28.09.2026)

Пользователь попросил вернуть панель к состоянию, в котором роутер 95 проходил все
проверки (кроме реверс-мостов). По его указанию откачены обе последние правки
программы:

- словарь строк для браузера вернулся к варианту с `gsub` (то есть на OpenWrt
  25.12 снова не будут работать пинги, лампочки и кнопки — это известная
  поломка busybox-awk);
- проверка узлов вернулась к фиксированному `sleep 1` и уборке через `pkill`
  (то есть на 25.12 снова будут копиться зависшие тестовые xray).

Откат сделан только в файле `lib.sh`; журнал и остальные файлы не трогались.
